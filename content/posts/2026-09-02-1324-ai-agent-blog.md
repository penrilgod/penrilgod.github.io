## Intro: "도커가 없어도 되는 시대"가 오고 있다

> **"만약 2008년에 WASM과 WASI가 존재했다면, 우리는 도커(Docker)를 만들 필요가 없었을 것이다."**  
> *- 솔로몬 하이크(Solomon Hykes), Docker 창시자 -*

도커의 창시자가 직접 던진 이 한 마디는 최근 클라우드 네이티브 아키텍처 진영에 신선한 충격을 주었습니다. 지난 10년간 우리는 서버 배포의 표준으로 '도커 컨테이너'를 당연하게 받아들였습니다. 하지만 OS 커널을 공유함에도 불구하고 여전히 기가바이트(GB) 단위에 육박하는 컨테이너 이미지 크기, 수 초 이상 걸리는 콜드 스타트(Cold Start) 지연, 그리고 가상화 레이어로 인한 상당한 메모리 점유율은 서버리스(Serverless)와 에지(Edge) 인프라 환경에서 지속적인 병목으로 작용했습니다.

이러한 상황에서 브라우저 내부의 고성능 그래픽 연산을 돕던 **WebAssembly(Wasm)**가 **WASI(WebAssembly System Interface)** 표준안의 정의와 함께 운영체제(OS) 시스템 자원에 직접 접근할 수 있게 되면서, 백엔드 진영의 차세대 게임 체인저로 급부상하고 있습니다. 

오늘 글에서는 시니어 엔지니어의 관점에서 Wasm이 서버사이드 백엔드에서 왜 강력한 힘을 발휘하는지 살펴보고, **Rust**와 차세대 Wasm 프레임워크인 **Spin(by Fermyon)**을 활용해 실제 구동 가능한 초경량 API 서비스를 구축하는 실무 가이드를 제공하겠습니다.

## 1. Wasm vs Docker: 아키텍처 관점의 기술 비교

Wasm이 왜 도커의 자리를 위협할 수 있는지 이해하려면, 두 기술의 가상화 레이어 차이를 명확히 인지해야 합니다.

```
[Docker Container]                  [WebAssembly (WASI)]
+-----------------------------+     +-----------------------------+
|   Application Code & Deps   |     |   Compiled .wasm Binary     |
+-----------------------------+     +-----------------------------+
|  Guest OS Libraries (glibc) |     |   Wasm Runtime (Wasmtime)   |
+-----------------------------+     +-----------------------------+
|  Container Engine (Docker)  |     |   Host Operating System     |
+-----------------------------+     +-----------------------------+
|  Host OS & Kernel           |     +-----------------------------+
+-----------------------------+
```

* **Docker의 방식:** 어플리케이션을 실행하기 위해 최소한의 Guest OS 라이브러리 파일 시스템(glibc 등) 전체를 패키징합니다. 이로 인해 이미지 크기가 커지고, 격리를 위한 가상 네트워크 및 스토리지 네임스페이스를 초기화하는 데 수백 밀리초에서 수 초가 소요됩니다.
* **Wasm의 방식:** 소스코드를 플랫폼 독립적인 바이트코드(`.wasm`)로 컴파일하고, 호스트 OS 위에서 동작하는 초경량 런타임(예: Wasmtime)이 이를 직접 해석하거나 JIT(Just-In-Time) 컴파일하여 실행합니다. OS 수준의 가상화가 필요 없어 물리 머신에서 직접 실행하는 것에 준하는 가벼움과 속도를 자랑합니다.

### 핵심 기술 비교 지표

| 비교 항목 | Docker 컨테이너 | WebAssembly (Wasm/WASI) |
| :--- | :--- | :--- |
| **최소 이미지 크기** | 보통 50MB ~ 500MB 이상 | **수십 KB ~ 수 MB 수준** |
| **기동 속도 (Startup)** | 수백 ms ~ 수 초 (Cold Start 체감 가능) | **1ms 이하 (사실상 제로 콜드 스타트)** |
| **메모리 오버헤드** | 인스턴스당 수십 MB 이상 고정 점유 | **인스턴스당 수 KB ~ 수 MB 미만** |
| **보안 모델** | 리눅스 네임스페이스 및 cgroups 격리 | **역량 기반(Capability-based) 샌드박스 격리** |
| **이식성 (Portability)** | CPU 아키텍처(x86_64, ARM)별 이미지 빌드 필요 | **단일 바이너리로 아키텍처 무관하게 실행 가능** |

## 2. 실전 가이드: Rust와 Spin 프레임워크로 10분 만에 초경량 API 구축하기

이제 개념을 넘어, 실제 작동하는 Wasm 백엔드를 만들어 보겠습니다. 이번 실습에서는 Wasm 컴파일 효율이 가장 뛰어난 시스템 프로그래밍 언어인 **Rust**와, 마이크로서비스 빌드를 직관적으로 지원하는 오픈소스 도구인 **Spin**을 사용합니다.

### 1단계: 개발 환경 세팅 (Prerequisites)
Wasm 바이너리를 빌드하기 위해 Rust의 컴파일 타겟을 추가하고, Spin CLI를 설치합니다.

```bash
# 1. Rust Wasm 컴파일러 타겟 추가
rustup target add wasm32-wasi

# 2. Spin CLI 설치 (macOS 기준, Linux/Windows는 공식 문서 참고)
brew install fermyon/tap/spin
```

### 2단계: 신규 프로젝트 생성
Spin CLI를 사용하여 HTTP 요청을 트리거로 처리하는 Rust 템플릿 프로젝트를 생성합니다.

```bash
spin new -t http-rust hello-wasm-service --accept-defaults
cd hello-wasm-service
```

프로젝트가 생성되면 프로젝트 루트에 `spin.toml` 설정 파일과 `src/lib.rs` 소스 파일이 위치하게 됩니다.

### 3단계: Rust API 코드 작성
`src/lib.rs` 파일을 열어 사용자 요청을 받아 초경량 JSON을 응답하는 API 핸들러 코드를 작성합니다.

```rust
use anyhow::Result;
use spin_sdk::{
    http::{Request, Response, IntoResponse},
    http_component,
};
use serde::Serialize;

// JSON 응답을 구조화하기 위한 DTO 정의
#[derive(Serialize)]
struct StatusResponse {
    status: String,
    message: String,
    engine: String,
}

/// Spin HTTP 컴포넌트의 메인 진입점(Entry Point)
#[http_component]
fn handle_hello_wasm_service(req: Request) -> Result<impl IntoResponse> {
    println!("Received request: {:?}", req.uri());

    // 응답 데이터 구성
    let data = StatusResponse {
        status: "success".to_string(),
        message: "Hello from Wasm (WASI v2) Serverless Backend!".to_string(),
        engine: "Spin & Wasmtime (Fermyon)".to_string(),
    };

    // 구조체를 JSON 문자열로 직렬화
    let json_body = serde_json::to_string(&data)?;

    // HTTP 200 OK Response 반환
    Ok(Response::builder()
        .status(200)
        .header("content-type", "application/json")
        .body(json_body)
        .build())
}
```

### 4단계: 빌드 및 로컬 실행
작성된 코드를 Wasm 바이트코드로 컴파일하고 Spin의 초경량 WASI 런타임 위에서 가동합니다.

```bash
# 1. 컴파일 및 Spin 패키징 진행
spin build

# 2. 로컬 서버 실행
spin up
```

실행 결과 화면에 아래와 같이 표시되면 성공입니다:
```text
Serving http://127.0.0.1:3000
Available Routes:
  hello-wasm-service: http://127.0.0.1:3000 (aka /)
```

브라우저나 `curl`을 통해 호출해 보면 즉각적인 응답 속도를 확인할 수 있습니다.
```bash
curl http://127.0.0.1:3000
# 응답 결과: {"status":"success","message":"Hello from Wasm (WASI v2) Serverless Backend!","engine":"Spin & Wasmtime (Fermyon)"}
```
빌드된 결과물(`.wasm` 파일)의 크기를 확인해 보면 **단 몇 메가바이트(MB) 수준**에 불과해, 최소 수십 MB에 달하는 도커 컨테이너 이미지와 엄청난 대조를 이룹니다.

## 3. 검증: Python을 이용한 고성능 동시성 벤치마킹 실습

우리가 빌드한 Wasm API의 응답성과 효율성을 검증하기 위해, 파이썬(Python)의 비동기 라이브러리인 `httpx`와 `asyncio`를 활용하여 동시성 벤치마크 테스트 스크립트를 작성하고 실행해 보겠습니다. 

이 스크립트는 100개의 동시 요청을 병렬로 처리하며, Wasm 컨테이너가 부하 상황에서 얼마나 신속하고 고르게 반응하는지 측정합니다.

```python
# benchmark.py
import asyncio
import time
import httpx

TARGET_URL = "http://127.0.0.1:3000"
CONCURRENT_REQUESTS = 100

async def send_request(client: httpx.AsyncClient, req_id: int):
    start_time = time.perf_counter()
    try:
        response = await client.get(TARGET_URL)
        latency = (time.perf_counter() - start_time) * 1000  # ms 변환
        return response.status_code, latency
    except Exception as e:
        return None, 0.0

async def main():
    print(f"🔥 Starting benchmark: sending {CONCURRENT_REQUESTS} concurrent requests to {TARGET_URL}...")
    
    # Connection Pool 크기 및 타임아웃 제한 설정
    limits = httpx.Limits(max_keepalive_connections=50, max_connections=CONCURRENT_REQUESTS)
    async with httpx.AsyncClient(limits=limits, timeout=10.0) as client:
        
        # 전체 요청 동시 실행 예약
        tasks = [send_request(client, i) for i in range(CONCURRENT_REQUESTS)]
        
        total_start = time.perf_counter()
        results = await asyncio.gather(*tasks)
        total_duration = (time.perf_counter() - total_start) * 1000
        
    # 결과 수집 및 분석
    latencies = [lat for status, lat in results if status == 200]
    success_count = len(latencies)
    
    if success_count > 0:
        avg_latency = sum(latencies) / success_count
        max_latency = max(latencies)
        min_latency = min(latencies)
        
        print("\n================== BENCHMARK RESULT ==================")
        print(f"✅ Success Rate       : {success_count}/{CONCURRENT_REQUESTS} ({success_count/CONCURRENT_REQUESTS * 100:.1f}%)")
        print(f"⏱️  Total Elapsed Time  : {total_duration:.2f} ms")
        print(f"🚀 Average Latency    : {avg_latency:.2f} ms")
        print(f"📉 Min/Max Latency    : {min_latency:.2f} ms / {max_latency:.2f} ms")
        print(f"⚡ Throughput         : {success_count / (total_duration / 1000):.2f} req/sec")
        print("=======================================================")
    else:
        print("❌ Benchmark failed: No successful responses.")

if __name__ == "__main__":
    asyncio.run(main())
```

이 스크립트를 로컬 머신에서 실행하면, Wasm API가 동시 다발적인 요청 속에서도 별도의 지연(Latency) 흔들림 없이 극도로 신속하게 처리해 내는 모습을 정량적으로 확인하실 수 있습니다.

## 4. 💡 실무 적용 팁: 프로덕션 환경에서의 Wasm 도입 전략

현업 아키텍트이자 엔지니어로서, 기존 도커 환경을 무작정 모두 Wasm으로 마이그레이션하려는 시도는 경계해야 합니다. 아래의 실무 가이드라인을 참고하여 점진적으로 접근해야 시행착오를 줄일 수 있습니다.

### 1. Wasm 도입에 가장 최적인 시나리오 (Good Case)
* **에지 컴퓨팅 (Edge Computing):** Cloudflare Workers, Fastly Compute@Edge 등 사용자 접점과 가까운 CDN 에지 노드에서 로직을 실행해야 할 때 최적입니다.
* **서버리스 콜드 스타트 개선:** 트래픽이 불규칙적으로 튀어 유휴 시간에는 꺼두어야 하지만, 요청이 유입될 때 즉각 반응해야 하는 이벤트 기반 아키텍처(EDA) 마이크로서비스에 적합합니다.
* **플러그인 아키텍처:** 상용 제품 내부에 사용자가 직접 코딩한 커스텀 플러그인을 안전한 샌드박스 내부에서 고성능으로 기동시키고 싶을 때 이상적입니다.

### 2. 아직 도입을 보류해야 하는 시나리오 (Bad Case)
* **대규모 레거시 패키지가 필요한 앱:** Wasm은 파일 시스템 아키텍처가 제약적입니다. C-Binding 기반의 무거운 파이썬 머신러닝 라이브러리(TensorFlow, PyTorch 등)를 직접 구동하는 것은 컴파일 크기와 런타임 제한 때문에 오히려 도커보다 불리합니다.
* **성숙하지 못한 DB 커넥션 풀링:** WASI 표준의 소켓 API 지원 범위(WASI Preview 2 등)가 점진적으로 고도화되고는 있으나, 아직 완전한 프로덕션 수준의 고성능 멀티스레드 DB 커넥션 풀 라이브러리를 사용하기에는 드라이버 제약이 존재합니다. 중간에 HTTP 기반 데이터 API 게이트웨이(예: Supabase, Prisma Data Proxy 등)를 두는 구조를 권장합니다.

### 3. 클라우드 연동 팁
현재 완벽한 Wasm 백엔드를 구축하는 가장 주류적인 클라우드 통합 방식은 다음과 같습니다:
* **Kubernetes 환경 통합:** **Krunvm**이나 **Kustone**을 사용하여 기존 쿠버네티스 노드 내에서 도커 컨테이너와 Wasm 워크로드를 동시 배치(Co-location)하고 단일 네트워크 인프라로 관리합니다.
* **AWS Lambda 통합:** AWS가 공식 지원하는 LLRT(Low-Latency Runtime) 또는 Spin 컴포넌트를 컨테이너 이미지 형태로 패키징하여 배포하되, 실제 실행부는 Wasmtime을 타도록 설정하면 기동 시 레이턴시를 크게 극대화할 수 있습니다.

## 결론: 패러다임의 변화에 올라타라

WebAssembly(Wasm/WASI)의 급부상은 도커를 완전히 밀어내기 위함이 아닙니다. 오히려 도커가 감당하기에는 지나치게 무거웠던 **"짧고, 가볍고, 즉각적이어야 하는 백엔드 영역"**을 마침내 효율적으로 구동할 수 있게 조력하는 **'컴퓨팅의 조각(Piece)'**을 완성시켰다고 보는 것이 옳습니다.

메가바이트 단위의 배포 크기, 밀리초 단위의 가동 속도, 극도로 단단한 보안성이라는 삼박자를 갖춘 Wasm 백엔드 생태계는 앞으로 서버리스 아키텍처의 기본 문법으로 자리 잡을 것입니다. 지금 바로 Rust와 Spin을 사용하여 가벼운 컴포넌트 단위부터 직접 검증을 시작해 보십시오. 가벼워진 메모리 사용량만큼, 여러분의 인프라 비용 청구서도 혁신적으로 가벼워질 것입니다.
