## 서론: 왜 지금 '엣지 백엔드'를 고민해야 하는가?

안녕하세요. 20년 동안 데이터 파이프라인과 대규모 분산 아키텍처를 설계해 온 시니어 엔지니어입니다. 

스타트업의 아키텍처를 진두지휘하거나 개인 사이드 프로젝트를 운영할 때, 우리는 흔히 편리함을 무기로 **Vercel**이나 **AWS Lambda** 기반의 서버리스 아키텍처를 선택합니다. 하지만 서비스가 성장하고 트래픽이 몰리기 시작하는 순간, 두 가지 거대한 장벽에 직면하게 됩니다.

1. **지독한 콜드 스타트(Cold Start):** 컨테이너나 가상머신(VM)을 띄우는 기존 방식은 오랜 시간 요청이 없다가 들어올 때 수백 밀리초에서 수 초에 달하는 지연 시간을 발생시킵니다.
2. **FinOps의 지옥(비용 폭탄):** 대역폭(Bandwidth) 비용 및 실행 시간 과금 정책으로 인해, 약간의 트래픽 급증만으로도 상상을 초월하는 청구서가 전달되곤 합니다.

오늘 소개할 아키텍처는 글로벌 CDN 강자인 Cloudflare의 **V8 Isolate 기반 엣지 컴퓨팅(Cloudflare Workers)**과 오픈소스 Firebase 대안인 **Supabase**의 조합입니다. 이 둘을 유기적으로 연결하면 **초기 비용 '0원'**으로 시작해, 전 세계 어느 리전에서 접속하든 **10ms 안팎의 응답 속도**를 보장하는 엔터프라이즈급 API 서버를 완성할 수 있습니다. 

어떻게 이것이 가능한지, 20년 경력 개발자의 관점에서 동작 메커니즘부터 실제 구현 및 성능 검증까지 한 번에 정리해 드리겠습니다.

## 본론 1: 왜 Cloudflare Workers와 Supabase의 조합인가?

기존 서버리스 시스템과 엣지 기반 서버리스의 차이를 이해하는 것이 이 아키텍처의 출발점입니다.

| 비교 항목 | 기존 Node.js 서버리스 (AWS Lambda, Vercel) | 엣지 서버리스 (Cloudflare Workers) |
| :--- | :--- | :--- |
| **기반 기술** | 컨테이너 / 가상화 가상 머신 (VM) | Google V8 JavaScript Engine Isolates |
| **콜드 스타트** | 약 200ms ~ 2,000ms | **사실상 0ms (수 밀리초 이내)** |
| **글로벌 분산** | 개발자가 지정한 특정 리전에 고정 | 전 세계 300개 이상의 Cloudflare 데이터 센터에 자동 배포 |
| **무료 티어 혜택** | 월 100만 회 요청 (리전 제한 존재) | **매일 10만 회 요청 (전 세계 엣지 무료)** |

### V8 Isolates의 마법
Cloudflare Workers가 콜드 스타트 없이 즉시 실행될 수 있는 비결은 **V8 Isolates** 기술 덕분입니다. 무거운 OS 가상화나 컨테이너를 구동하는 대신, 단일 프로세스 내에서 수천 개의 가볍고 격리된 런타임 인스턴스(Isolates)를 실행합니다. 메모리 오버헤드가 메가바이트 단위에 불과하여, 첫 요청이 들어오는 순간 1밀리초 만에 코드가 즉시 실행됩니다.

### Supabase PostgreSQL과의 물리적 시너지
엣지 컴퓨팅의 유일한 단점은 **"컴퓨팅 엔진은 전 세계에 퍼져 있는데, 데이터베이스는 한곳(예: us-east-1)에 고정되어 있다"**는 점이었습니다. 

이를 해결하기 위해 Supabase가 강점을 가집니다. Supabase는 고성능 PostgreSQL을 기반으로 하며, 내장된 커넥션 풀러(PgBouncer)를 기본 탑재하고 있습니다. 여기에 Cloudflare의 **Hyperdrive** 기술을 얹으면, 전 세계 엣지 노드가 미국 혹은 아시아에 있는 Supabase DB 인스턴스와 수립해 둔 TCP 세션을 재사용(Connection Pooling)하여 핸드셰이크 시간을 획기적으로 단축시킵니다.

## 본론 2: 아키텍처 설계 및 데이터 흐름

우리가 오늘 구축해 볼 예시는 **"실시간 글로벌 링크 단축 및 분석(Link Shortener & Analytics) 서비스"**입니다. 사용자가 단축 URL을 요청했을 때, 지리적으로 가장 가까운 엣지 서버가 Supabase에서 원본 URL을 쿼리해 리다이렉트하고, 동시에 접속 통계를 기록하는 최적화 구조입니다.

### 시스템 데이터 흐름도

```text
[사용자 요청 (Seoul)] ──> [Cloudflare Edge Worker (Seoul)]
                                  │
                         (Hyperdrive 가속 커넥션)
                                  │
                                  ▼
                     [Supabase DB (AWS ap-northeast-2)]
                                  │
                         (원본 URL 정보 반환)
                                  │
[사용자 Redirect] <── [Edge Worker에서 302 반환 (15ms 이내)]
```

이 구조에서 Cloudflare Workers는 요청한 클라이언트의 IP 주소를 기반으로 국가 정보(`request.cf.country`) 및 위도/경도를 헤더로 바로 추출해 줍니다. 데이터베이스 세션 연결은 Cloudflare Hyperdrive를 경유해 이미 열려 있는 커넥션을 타기 때문에, TCP 핸드셰이크 단계 없이 즉각적인 SQL 질의가 처리됩니다.

## 본론 3: 실전 구현 및 성능 벤치마킹 검증

인프라가 아무리 훌륭해도 실제 성능을 직접 눈으로 확인해 보기 전에는 신뢰할 수 없는 법입니다. 이번 단계에서는 **Cloudflare Workers API가 얼마나 신속하게 응답하는지 테스트하기 위해, Python의 비동기 멀티스레딩 기술을 활용한 고성능 벤치마킹 도구**를 작성해 검증해 보겠습니다.

### 2. Python 기반 엣지 API 성능 테스트 및 분석 스크립트
아래 코드는 실무에서 개발한 API 서버의 성능을 원격에서 멀티스레드로 타격하여 **Latency(지연 시간) 분포와 처리량(Throughput)**을 객관적으로 분석할 수 있는 파이썬 스크립트입니다. 

표준 라이브러리만을 활용하여 의존성을 최소화했으며, 엣지 API 엔드포인트에 동시 요청을 부과하여 실제 콜드 스타트 여부와 평균 레이턴시를 측정해 줍니다.

```python
import concurrent.futures
import time
import urllib.request
import urllib.error
import json

# 테스트 타겟 설정 (여기에 본인의 Cloudflare Workers URL 또는 비교군 URL 입력)
TARGET_URL = "https://your-worker-subdomain.workers.dev/abcde" 
CONCURRENT_REQUESTS = 20  # 동시 요청 수
TOTAL_REQUESTS = 100      # 총 요청 횟수

def send_request(request_id):
    """지정된 URL에 HTTP GET 요청을 보내고 소요 시간을 측정합니다."""
    start_time = time.perf_counter()
    headers = {
        'User-Agent': f'EdgeBenchmarkBot/1.0 (Request-{request_id})',
        'Accept': 'application/json'
    }
    req = urllib.request.Request(TARGET_URL, headers=headers)
    
    try:
        with urllib.request.urlopen(req, timeout=5) as response:
            status = response.getcode()
            response.read()  # 데이터 스트림 완전 소모
            end_time = time.perf_counter()
            elapsed = (end_time - start_time) * 1000  # ms 단위 변환
            return status, elapsed
    except urllib.error.HTTPError as e:
        end_time = time.perf_counter()
        return e.code, (end_time - start_time) * 1000
    except Exception as e:
        end_time = time.perf_counter()
        return "ERROR", (end_time - start_time) * 1000

def run_benchmark():
    print(f"🚀 벤치마킹 시작: {TARGET_URL}")
    print(f"🔥 조건: 동시 요청 {CONCURRENT_REQUESTS}개 / 총 {TOTAL_REQUESTS}개 요청 진행 중...\n")
    
    latencies = []
    success_count = 0
    failure_count = 0
    
    start_bench = time.perf_counter()
    
    # ThreadPoolExecutor를 통한 실전 멀티스레드 동시성 모사
    with concurrent.futures.ThreadPoolExecutor(max_workers=CONCURRENT_REQUESTS) as executor:
        futures = [executor.submit(send_request, i) for i in range(TOTAL_REQUESTS)]
        
        for future in concurrent.futures.as_completed(futures):
            status, elapsed = future.result()
            if status in [200, 302, 301]: # 리다이렉션 포함 성공 처리
                success_count += 1
                latencies.append(elapsed)
            else:
                failure_count += 1
                
    end_bench = time.perf_counter()
    total_duration = end_bench - start_bench
    
    if not latencies:
        print("❌ 모든 요청이 실패하여 통계를 산출할 수 없습니다.")
        return

    # 성능 지표 산출
    latencies.sort()
    avg_latency = sum(latencies) / len(latencies)
    p50_latency = latencies[int(len(latencies) * 0.5)]
    p95_latency = latencies[int(len(latencies) * 0.95)]
    p99_latency = latencies[int(len(latencies) * 0.99)]
    throughput = TOTAL_REQUESTS / total_duration

    # 결과 대시보드 출력
    print("=" * 50)
    print("               BENCHMARK RESULT                ")
    print("=" * 50)
    print(f"✔️  총 소요 시간     : {total_duration:.2f} 초")
    print(f"✔️  초당 처리량 (RPS): {throughput:.2f} req/sec")
    print(f"✔️  요청 성공률     : {success_count}/{TOTAL_REQUESTS} ({(success_count/TOTAL_REQUESTS)*100:.1f}%)")
    print("-" * 50)
    print(f"📊 평균 지연 시간 (Avg Latency) : {avg_latency:.2f} ms")
    print(f"📊 중위 지연 시간 (P50 Latency) : {p50_latency:.2f} ms")
    print(f"📊 95% 신뢰 구간  (P95 Latency) : {p95_latency:.2f} ms")
    print(f"📊 99% 극단 구간  (P99 Latency) : {p99_latency:.2f} ms")
    print("=" * 50)

if __name__ == "__main__":
    run_benchmark()
```

이 테스트 코드를 가동해 보면, 일반적인 VM 기반 API 서버는 초기 호출 시 콜드 스타트로 인해 P99 레이턴시가 수 초대로 튀는 반면, Cloudflare Workers는 첫 번째 루프부터 수십 ms 수준의 지극히 안정적인 플랫 라인을 유지함을 확인할 수 있습니다.

## 💡 실무 적용 팁: 성공적인 프로덕션 운영을 위한 체크리스트

막상 토이 프로젝트를 넘어 상용 프로덕션 환경에 이 아키텍처를 이식할 때는 몇 가지 숨겨진 제약 사항과 마주치게 됩니다. 20년 차 엔지니어의 경험이 담긴 트러블슈팅 팁을 전해 드립니다.

1. **V8 Isolates의 메모리 및 크기 한계 극복**
   * Cloudflare Workers의 무료 플랜은 CPU 타임 한계가 요청당 **10ms**이며, 번들 크기가 **1MB**(압축 후)로 제한됩니다. 
   * 따라서 거대한 Node.js 라이브러리(예: AWS-SDK 전체, 중량급 ORM)를 통째로 임포트하는 것을 피하고, 오직 엣지 환경에 최적화된 **Kysely**나 **Prisma-Edge**, 혹은 순수 SQL을 전달하는 경량 클라이언트를 사용해야 합니다.

2. **데이터베이스 커넥션 소진 방지**
   * 트래픽이 일시에 급증하여 엣지 노드가 수천 개로 확장되면, 중앙 Supabase의 PostgreSQL 커넥션 제한(Max Connection)을 순식간에 초과할 수 있습니다.
   * **필수 조치:** Supabase 대시보드에서 제공하는 트랜잭션 풀러 포트(기본 6543)를 연동하여 사용하거나, Cloudflare Hyperdrive를 활성화하여 커넥션 재사용성을 극대화해야 합니다.

3. **환경 변수(Secrets) 보안 관리**
   * API 토큰이나 데이터베이스 패스워드 같은 민감한 정보는 소스코드에 절대 하드코딩해서는 안 됩니다. 
   * `wrangler.toml` 파일의 명세 대신 `wrangler secret put DB_URL` 명령을 활용하여 Cloudflare 전역 KMS(Key Management Service)에 안전하게 바인딩해 두고 Worker 컨텍스트에서 `env.DB_URL` 형태로 호출하십시오.

오늘 우리가 살펴본 **Cloudflare Workers와 Supabase**의 연동 구조는 고성능과 비용 최적화라는 상반된 두 마리 토끼를 완벽하게 잡아냅니다. 초기 진입 장벽이었던 엣지 DB 연결 지연 문제 또한 **Hyperdrive**라는 차세대 네트워크 레이어 기술의 도입으로 사실상 마침표를 찍었습니다.
