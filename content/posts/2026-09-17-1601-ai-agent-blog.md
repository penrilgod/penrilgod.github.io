## 1. 들어가며: 배포하고 나서야 터지는 에러, 언제까지 방치할 것인가?

클라우드 네이티브 아키텍처가 주류로 자리 잡으면서 S3, SQS, DynamoDB, Lambda 등의 AWS 매니지드 서비스는 백엔드 개발의 필수 요소가 되었습니다. 하지만 이 매니지드 서비스들을 "어떻게 테스트할 것인가?"에 이르면 많은 팀이 딜레마에 빠집니다.

가장 흔히 사용하는 두 가지 접근법은 각각 뚜렷한 한계를 가집니다.

1. **실제 AWS 개발 계정 사용:** 테스트 속도가 느려지고, 병렬 테스트 시 데이터 격리가 어렵습니다. 무엇보다 테스트 자원 정리 깜빡임으로 인한 '프리티어 폭탄(Billing Bomb)'의 위협이 상존합니다.
2. **Mocking 라이브러리 사용:** `moto`나 단순 단위 테스트 모크는 가볍고 빠르지만, 실제 AWS 인프라의 미묘한 동작 방식(예: SQS의 가시성 타임아웃, DynamoDB의 쿼리 제약 사항 등)을 완벽히 모방하지 못합니다. 결국 로컬에서는 통과한 코드가 운영 환경(Production)에서 터지는 이른바 **'비헤이비어 갭(Behavioral Gap)'** 현상을 겪게 됩니다.

이 문제를 우아하게 해결하는 치트키가 바로 **LocalStack**과 **Testcontainers**의 결합입니다. LocalStack은 로컬 환경에서 AWS API를 완벽하게 에뮬레이션해 주며, Testcontainers는 이를 테스트 라이프사이클에 맞춰 독커(Docker) 컨테이너로 자동 제어해 줍니다. 10년 차 시니어 엔지니어의 관점에서, 이 두 도구를 결합하여 안정적이고 유연한 **인프라리스(Infraless) 통합 테스트 파이프라인**을 구축하는 방법을 자세히 공유하겠습니다.

## 2. 왜 LocalStack과 Testcontainers의 조합인가?

많은 개발자가 로컬에 미리 `docker-compose.yml`을 띄워놓고 LocalStack을 사용합니다. 하지만 이 방식은 다음과 같은 치명적인 단점이 있습니다.

* **테스트 격리 실패:** 이전 테스트가 남긴 잔재 데이터가 다음 테스트 결과에 영향을 줍니다.
* **로컬 의존성:** 새로운 개발자가 합류했을 때 로컬 Docker 네트워크 환경을 수동으로 맞춰야 하는 번거로움이 있습니다.
* **CI/CD 연동의 까다로움:** GitHub Actions 등의 러너 환경에서 매번 Docker Compose를 백그라운드로 실행하고 헬스체크를 기다리는 스크립트를 짜는 것은 비효율적입니다.

**Testcontainers**를 사용하면 이러한 문제가 깔끔하게 해결됩니다.

```
[테스트 실행 (pytest)]
       │
       ▼ (동적 컨테이너 생성)
┌─────────────────────────────────┐
│  LocalStack Docker Container    │
│  (S3, DynamoDB, SQS 가동)        │
│  - 임의의 포트 자동 할당         │
└─────────────────────────────────┘
       │
       ▼ (테스트 수행 및 검증)
[테스트 종료 (자동 컨테이너 소멸 및 정리)]
```

테스트 코드가 실행되는 시점에 필요한 스펙의 LocalStack 컨테이너가 생성되고, 무작위로 비어 있는 포트(Dynamic Port)를 할당받아 실행된 후, 테스트가 종료되면 흔적도 없이 자동으로 소멸합니다. 개발자는 오직 테스트 코드 작성에만 집중할 수 있게 됩니다.

## 3. 실전 구축 가이드: S3 및 DynamoDB 통합 테스트 (Python)

이제 구체적인 시나리오를 바탕으로 실전 코드를 작성해 보겠습니다. 

### 비즈니스 시나리오
> 사용자가 프로필 이미지를 업로드하면, 백엔드 서비스는 **① AWS S3에 이미지를 업로드**하고, **② DynamoDB 테이블에 이미지 메타데이터(파일명, 용량, 업로드 시간 등)를 기록**합니다.

### 사전 준비물
파이썬 환경에서 본 실습을 진행하려면 아래 라이브러리들이 설치되어 있어야 합니다. (Docker가 로컬에 실행 중이어야 합니다.)

```bash
pip install testcontainers[localstack] boto3 pytest
```

### 실전 파이썬 테스트 코드
아래 코드는 `testcontainers-python` 라이브러리를 활용하여 테스트 실행 시점에 LocalStack을 띄우고, S3와 DynamoDB 클라이언트의 엔드포인트를 동적으로 재매핑하여 검증을 수행하는 완전한 예제입니다.

```python
import os
import unittest
import boto3
from botocore.exceptions import ClientError
from testcontainers.localstack import LocalStackContainer

class TestUserProfileService(unittest.TestCase):
    localstack = None
    s3_client = None
    dynamodb_client = None

    @classmethod
    def setUpClass(cls):
        """
        테스트 클래스 시작 전, 딱 한 번 LocalStack 컨테이너를 구동합니다.
        S3와 DynamoDB 서비스를 활성화합니다.
        """
        cls.localstack = LocalStackContainer(image="localstack/localstack:3.0.0")
        cls.localstack.start()

        # LocalStack 컨테이너가 제공하는 동적 엔드포인트 URL 획득
        cls.endpoint_url = cls.localstack.get_url()

        # AWS SDK(boto3) 클라이언트를 LocalStack 엔드포인트로 설정
        cls.s3_client = boto3.client(
            "s3",
            endpoint_url=cls.endpoint_url,
            aws_access_key_id="test-key",
            aws_secret_access_key="test-secret",
            region_name="us-east-1"
        )
        cls.dynamodb_client = boto3.client(
            "dynamodb",
            endpoint_url=cls.endpoint_url,
            aws_access_key_id="test-key",
            aws_secret_access_key="test-secret",
            region_name="us-east-1"
        )

    @classmethod
    def tearDownClass(cls):
        """
        모든 테스트가 끝나면 컨테이너를 안전하게 소멸시킵니다.
        """
        if cls.localstack:
            cls.localstack.stop()

    def setUp(self):
        """
        매 테스트 케이스 실행 전에 독립적인 환경을 구축합니다.
        (버킷 생성 및 테이블 초기화)
        """
        self.bucket_name = "user-profiles"
        self.table_name = "UserMetadata"

        # S3 버킷 생성
        self.s3_client.create_bucket(Bucket=self.bucket_name)

        # DynamoDB 테이블 생성
        self.dynamodb_client.create_table(
            TableName=self.table_name,
            KeySchema=[{"AttributeName": "username", "KeyType": "HASH"}],
            AttributeDefinitions=[{"AttributeName": "username", "AttributeType": "S"}],
            ProvisionedThroughput={"ReadCapacityUnits": 5, "WriteCapacityUnits": 5}
        )

    def tearDown(self):
        """
        매 테스트 케이스가 끝난 후 리소스를 삭제하여 격리를 유지합니다.
        """
        # S3 버킷 내 객체 삭제 후 버킷 삭제
        try:
            objects = self.s3_client.list_objects_v2(Bucket=self.bucket_name)
            if "Contents" in objects:
                for obj in objects["Contents"]:
                    self.s3_client.delete_object(Bucket=self.bucket_name, Key=obj["Key"])
            self.s3_client.delete_bucket(Bucket=self.bucket_name)
        except ClientError:
            pass

        # DynamoDB 테이블 삭제
        try:
            self.dynamodb_client.delete_table(TableName=self.table_name)
        except ClientError:
            pass

    def test_upload_profile_image_success(self):
        """
        S3 파일 업로드 및 DynamoDB 메타데이터 적재가 성공적으로 수행되는지 검증합니다.
        """
        # Given
        username = "chulsoo_kim"
        file_content = b"fake-image-bytes"
        file_name = "avatar.png"

        # When: (1) S3에 원본 이미지 파일 업로드
        self.s3_client.put_object(
            Bucket=self.bucket_name,
            Key=f"{username}/{file_name}",
            Body=file_content
        )

        # When: (2) DynamoDB에 이미지 업로드 메타데이터 저장
        self.dynamodb_client.put_item(
            TableName=self.table_name,
            Item={
                "username": {"S": username},
                "avatar_url": {"S": f"s3://{self.bucket_name}/{username}/{file_name}"},
                "file_size": {"N": str(len(file_content))}
            }
        )

        # Then: (1) S3에 파일이 실제로 존재하는지 검증
        response_s3 = self.s3_client.get_object(Bucket=self.bucket_name, Key=f"{username}/{file_name}")
        downloaded_bytes = response_s3["Body"].read()
        self.assertEqual(downloaded_bytes, file_content)

        # Then: (2) DynamoDB에 메타데이터가 올바르게 적재되었는지 검증
        response_db = self.dynamodb_client.get_item(
            TableName=self.table_name,
            Key={"username": {"S": username}}
        )
        self.assertIn("Item", response_db)
        self.assertEqual(response_db["Item"]["avatar_url"]["S"], f"s3://{self.bucket_name}/{username}/{file_name}")
        self.assertEqual(response_db["Item"]["file_size"]["N"], str(len(file_content)))

if __name__ == "__main__":
    unittest.main()
```

## 4. CI/CD (GitHub Actions) 연동 가이드

로컬에서 완벽하게 돌아가는 통합 테스트를 구현했다면, 이를 배포 파이프라인(CI/CD)에 녹여내는 일은 식은 죽 먹기입니다. GitHub Actions 러너에는 기본적으로 Docker 엔진이 탑재되어 있기 때문에 별도의 추가 가상화 도구 설치 없이 동작합니다.

아래 설정 파일을 `.github/workflows/integration-test.yml` 경로에 추가하는 것만으로 '인프라리스' 통합 테스트 단계가 CI 환경에 통합됩니다.

```yaml
name: Python Integration Test with LocalStack

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
    - name: Checkout code
      uses: actions/checkout@v3

    - name: Set up Python
      uses: actions/setup-python@v4
      with:
        python-version: '3.10'

    # GitHub Actions 호스트 머신의 Docker를 그대로 활용하므로 Testcontainers가 즉시 구동됩니다.
    - name: Install dependencies
      run: |
        python -m pip install --upgrade pip
        pip install testcontainers[localstack] boto3 pytest

    - name: Run Integration Tests
      run: |
        pytest -v
```

## 5. 💡 실무 적용 팁 (Senior's Secret)

실무에서 Testcontainers와 LocalStack을 도입하여 대규모 마이크로서비스 테스트를 설계할 때, 성공과 실패를 가르는 중요한 아키텍처적 디테일들이 있습니다.

* **싱글톤 컨테이너 패턴(Singleton Container Pattern)을 고려하세요:** 
  테스트 클래스나 파일마다 컨테이너를 매번 띄우면 전체 테스트 실행 시간이 극도로 길어집니다. 이를 방지하려면 전역 부모 클래스나 `pytest` 컨텍스트의 `Session` 레벨 피스처(Fixture)를 활용해 단 하나의 LocalStack 컨테이너만 구동하고, 테스트 케이스 간 데이터는 테이블명 변경이나 버킷 재생성 등의 논리적 방법으로 격리하는 편이 효율적입니다.
* **리소스 초기화 스크립트(.sh) 자동 주입 활용:** 
  LocalStack은 `/etc/localstack/init/ready.d/` 디렉터리에 놓인 쉘 스크립트나 AWS CLI 명령어 파일을 컨테이너 기동 시 자동으로 실행해 주는 초기화 기능을 지원합니다. 테스트 전용 DynamoDB 스키마 정의나 SQS 대기열 사전 생성이 필요하다면, Testcontainers의 파일 마운트(`with_exposed_ports` 등) 기능으로 초기화 스크립트를 밀어 넣어 부트스트랩 시간을 획기적으로 줄이세요.
* **LocalStack Pro의 가치를 저울질해 보세요:**
  기본 오픈소스 버전만으로도 S3, SQS, DynamoDB 등 핵심 서비스는 완벽히 지원되지만, Cognito, RDS, Athena, IAM 정책 제어 등의 세련된 동작이 필수라면 엔터프라이즈 레벨의 'LocalStack Pro' 도입을 고려해 볼 만합니다. 비싼 가상 인프라 검증 비용에 비하면 라이선스 비용이 훨씬 저렴할 수 있습니다.
