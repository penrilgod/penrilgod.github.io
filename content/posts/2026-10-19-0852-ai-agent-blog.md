## INTRO: 마이크로서비스 개발자들을 괴롭히는 '분산 트랜잭션'의 고통

20년 가까이 백엔드 아키텍처의 진화를 현업에서 지켜보면서, 단일 모놀리스(Monolith)에서 마이크로서비스 아키텍처(MSA)로 넘어갈 때 개발팀이 가장 크게 겪는 통증은 언제나 **'분산 트랜잭션 관리'**였습니다.

단일 RDBMS를 사용할 때는 `@Transactional` 어노테이션 하나로 끝났던 작업들이 MSA에서는 지옥으로 변합니다. '주문 생성 -> 결제 승인 -> 재고 차감 -> 배송 요청'으로 이어지는 파이프라인을 생각해 봅시다.

```
[주문 서비스] ──> [결제 서비스] ──> [재고 서비스] ──> [배송 서비스]
   (성공)            (성공)            (실패!)          (미진행)
                                          │
                                          └───> 결제 취소(보상)는 어떻게?
```

네트워크 타임아웃, 특정 컨테이너의 OOM(Out of Memory) KILLED, 외부 PG사의 응답 지연이 발생할 때 상태를 어떻게 복구할 것인가? 

기존에는 이를 해결하기 위해 Kafka/RabbitMQ 기반의 **Choreography Saga**나 중앙 집중식 DB를 거치는 **Orchestration Saga** 패턴을 도입했습니다. 하지만 이 방식은 다음과 같은 치명적인 문제를 야기합니다.

* **상태 관리의 파편화:** 트랜잭션의 중간 상태를 저장하기 위해 Redis, DB 락, 메시지 큐를 비동기로 엮으면서 스파게티 코드가 생성됩니다.
* **보상 로직(Compensation)의 복잡성:** 실패 시 이전 성공 단계들을 역순으로 취소하는 로직을 직접 작성하다 보면, 보상 트랜잭션 자체가 실패했을 때의 예외 처리가 다시 누적됩니다.
* **타임아웃 핸들링의 한계:** 외부 API 응답이 30분 뒤에 올 때, HTTP 연결을 유지하지 않고 비동기로 대기하다 안전하게 스레드를 깨우는 작업은 엔지니어링 비용이 매우 큽니다.

이러한 고통스러운 분산 시스템의 난제들을 **"코드가 죽어도 실행 상태는 영속된다"**는 아이디어 하나로 해결한 기술이 바로 **Temporal.io**와 **Durable Execution** 패러다임입니다.

## WHAT: Temporal.io와 Durable Execution 패러다임

### Durable Execution(내구성 있는 실행)이란?

**Durable Execution**은 애플리케이션의 실행 상태(로컬 변수, 스택 프레임, 미완료 함수 호출 등)를 외부 지속성 엔진에 완벽히 기록하여, 프로세스나 서버가 예기치 않게 종료되더라도 **정확히 정지된 그 시점, 그 상태 그대로 이어서 실행**되도록 보장하는 프로그래밍 패러다임입니다.

```
[일반적인 실행]
코드 실행중... ──> [서버 Down/OOM] ──> 프로세스 사망 (상태 손실, 데이터 불일치 발생)

[Durable Execution]
코드 실행중... ──> [서버 Down/OOM] ──> [새 서버에서 Worker 재개] ──> 정지된 변수/스택 그대로 계속 진행
```

### Temporal.io의 핵심 구성 요소

Temporal은 이 패러다임을 오픈소스로 구현한 대표적인 엔진입니다. 백엔드는 시스템을 크게 4가지 개념으로 분리하여 관리합니다.

1. **Temporal Server:** 이벤트 히스토리, 상태, 타이머, 큐를 관리하는 오케스트레이션 엔진 (비즈니스 로직을 실행하지 않음).
2. **Worker Process:** 개발자가 작성한 비즈니스 로직(Workflow 및 Activity)을 실행하는 애플리케이션 프로세스.
3. **Workflow (워크플로우):** 비즈니스 로직의 오케스트레이션을 담당하는 코드. 반드시 **결정론적(Deterministic)**이어야 함.
4. **Activity (액티비티):** DB 읽기/쓰기, 외부 REST API 호출 등 부작용(Side-effect)을 수반하는 실제 작업 단위.

### 2. Temporal 기반 주문 처리 코드 예제

다음 코드는 외부 PG사 결제와 재고 차감을 진행하며, 재고 차감 실패 시 결제를 자동으로 취소하는 보상 트랜잭션을 담고 있습니다.

```python
import asyncio
from datetime import timedelta
from temporalio import activity, workflow
from temporalio.client import Client
from temporalio.worker import Worker
from temporalio.exceptions import ActivityError

# ---------------------------------------------------------------------------
# 1. Activities 정의 (외부 API, DB 작업 등 Side-effect 포함)
# ---------------------------------------------------------------------------
@activity.defn
async def process_payment(order_id: str, amount: int) -> str:
    """결제 승인 API 호출"""
    print(f"[Activity] 주문 ID {order_id}에 대한 {amount}원 결제 진행 중...")
    # 실제 환경에서는 PG사 SDK 호출
    payment_id = f"PAY_{order_id}_999"
    print(f"[Activity] 결제 성공! Payment ID: {payment_id}")
    return payment_id

@activity.defn
async def cancel_payment(payment_id: str) -> None:
    """보상 트랜잭션: 결제 취소 API 호출"""
    print(f"[Activity-Compensation] 결제 ID {payment_id} 취소 요청 처리 중...")
    # 실제 환경에서는 PG사 결제 취소 호출

@activity.defn
async def reserve_inventory(order_id: str, item_id: str) -> None:
    """재고 차감 작업 (실패 시나리오 연출 가능)"""
    print(f"[Activity] 상품 {item_id} 재고 차감 시도...")
    
    # 실무 시나리오 모사: 특정 조건에서 재고 부족 예외 발생
    if item_id == "OUT_OF_STOCK_ITEM":
        raise ValueError("해당 상품의 재고가 부족합니다.")
    
    print(f"[Activity] 상품 {item_id} 재고 차감 완료")

# ---------------------------------------------------------------------------
# 2. Workflow 정의 (State-as-Code 및 보상 로직 구현)
# ---------------------------------------------------------------------------
@workflow.defn
class OrderProcessingWorkflow:
    @workflow.run
    async def run(self, order_id: str, item_id: str, amount: int) -> str:
        # 단일 서버 코드를 작성하듯 직관적인 트랜잭션 흐름 작성
        payment_id = None
        
        try:
            # Step 1: 결제 진행 (실패 시 자동 재시도 정책 포함)
            payment_id = await workflow.execute_activity(
                process_payment,
                args=[order_id, amount],
                start_to_close_timeout=timedelta(seconds=10),
            )

            # Step 2: 재고 차감 진행
            await workflow.execute_activity(
                reserve_inventory,
                args=[order_id, item_id],
                start_to_close_timeout=timedelta(seconds=10),
            )

            return f"주문 완료 (Order ID: {order_id})"

        except ActivityError as e:
            workflow.logger.error(f"워크플로우 오류 발생: {e.cause}")
            
            # Saga Pattern: 재고 차감 실패 시 결제 건이 존재하면 보상 트랜잭션 수행
            if payment_id:
                workflow.logger.info("보상 트랜잭션 시작: 결제 취소를 진행합니다.")
                await workflow.execute_activity(
                    cancel_payment,
                    args=[payment_id],
                    start_to_close_timeout=timedelta(seconds=10),
                )
            
            raise e

# ---------------------------------------------------------------------------
# 3. Worker 및 실행 테스트 메인 루틴
# ---------------------------------------------------------------------------
async def main():
    # 로컬에서 실행 중인 Temporal Server에 연결 (기본 포트 7233)
    client = await Client.connect("localhost:7233")

    # Worker 생성 및 워크플로우/액티비티 등록
    async with Worker(
        client,
        task_queue="order-processing-queue",
        workflows=[OrderProcessingWorkflow],
        activities=[process_payment, cancel_payment, reserve_inventory],
    ):
        print("=== Temporal Worker가 시작되었습니다. Task Queue: order-processing-queue ===")

        # 테스트 1: 실패 시나리오 (재고 부족)
        print("\n--- [시나리오 1] 재고 부족으로 인한 보상 트랜잭션 수행 테스트 ---")
        try:
            result = await client.execute_workflow(
                OrderProcessingWorkflow.run,
                args=["ORD_20261019_01", "OUT_OF_STOCK_ITEM", 50000],
                id="order-workflow-failed-test",
                task_queue="order-processing-queue",
            )
        except Exception as err:
            print(f"워크플로우가 예상대로 실패 후 보상 처리되었습니다: {err}")

        # 테스트 2: 성공 시나리오
        print("\n--- [시나리오 2] 정상 주문 처리 테스트 ---")
        result = await client.execute_workflow(
            OrderProcessingWorkflow.run,
            args=["ORD_20261019_02", "NORMAL_ITEM", 30000],
            id="order-workflow-success-test",
            task_queue="order-processing-queue",
        )
        print(f"워크플로우 결과: {result}")

if __name__ == "__main__":
    asyncio.run(main())
```

### 코드 해설
* **보상 로직의 단순화:** 과거 메시지 큐 방식이었다면 `StockFailedEvent`를 구독하는 독립된 리스너를 만들어 상태를 조회 후 결제 취소를 호출해야 했지만, Temporal에서는 파이썬의 표준 `try-except` 구문 내에서 `cancel_payment` Activity를 호출하는 것으로 보상 처리가 완벽히 해결됩니다.
* **장애 내구성:** `reserve_inventory` 실행 직전에 해당 Worker 서버가 다운되더라도, 새로운 Worker가 켜지면 이전 결제 결과(`payment_id`)를 **Temporal Server의 이벤트 히스토리에서 복원**하여 재고 차감 단계부터 실행을 재개합니다.

## COMPARE: 기존 기술 솔루션과의 명확한 비교 분석

많은 엔지니어들이 "Temporal이 Celery나 Kafka, AWS Step Functions와 무엇이 다른가?"에 대해 질문합니다. 핵심 차이점을 아래 표로 정리했습니다.

| 항목 | Kafka / RabbitMQ + Custom Saga | AWS Step Functions | Celery | **Temporal.io** |
| :--- | :--- | :--- | :--- | :--- |
| **패러다임** | Event-Driven Architecture | JSON/YAML 기반 State Machine | Asynchronous Task Queue | **Durable Execution (State-as-Code)** |
| **상태 관리** | 개발자가 DB / Redis에 직접 관리 | AWS 서비스 내부 상태 머신 관리 | Redis / RabbitMQ 등에 관리 | **Temporal Engine이 이벤트 스토어에 영속화** |
| **개발 경험** | 이벤트 파편화로 흐름 추적 어려움 | JSON 워크플로우 명세 작성의 번거로움 | 간단한 작업에 최적화, 복잡한 체이닝 제약 | **일반 프로그래밍 언어(Go/Python/TS) 제어문 사용** |
| **재시도/보상** | 직접 분기 및 보상 이벤트 구현 필요 | Amazon States Language 작성 | 실패 시 단일 Task 단위 재시도 | **워크플로우 내 표준 예외 처리 구문으로 즉시 해결** |
| **벤더 종속성** | 없음 | **AWS 락인 (Lock-in) 심함** | 없음 | **오픈소스 (Self-hosted or Cloud)** |

* **vs. Kafka:** Kafka는 고성능 이벤트 스트리밍 도구이지만 '워크플로우 상태'를 스스로 기억하지 못합니다. 상태 관리를 위해 Kafka Streams를 쓰더라도 비즈니스 코드의 복잡도는 증가합니다.
* **vs. AWS Step Functions:** 매우 훌륭한 서비스이지만, 비즈니스 로직을 코드(TypeScript/Python)가 아닌 복잡한 JSON/YAML 정의서로 작성해야 한다는 한계가 있습니다.

## 💡 실무 적용 팁: 시니어 엔지니어가 전하는 Temporal 프로덕션 가이드

Temporal을 실제 프로덕션 환경에 도입할 때는 몇 가지 철저히 지켜야 할 가이드라인이 있습니다.

### 1. 워크플로우 내 '결정론(Determinism)'의 법칙
Workflow 함수 내부에서는 **절대 Side-effect를 발생시키는 코드나 비결정론적 함수를 직접 호출해서는 안 됩니다.**
* ❌ **금지 항목:** `datetime.now()`, `random.randint()`, `requests.get()` 등의 direct API call, 전역 변수 수정.
* ⭕ **올바른 방식:** 모든 외부 시스템 통신, 시간 조회, 무작위 수 생성은 반드시 **Activity** 내부에서 수행하거나 Temporal SDK가 제공하는 APIs(`workflow.now()`)를 사용해야 합니다. 
* *이유:* Temporal은 장애 복구 시 이벤트 히스토리를 재실행(Replay)하므로, Workflow 코드가 매번 동일한 인풋에 대해 동일한 execution path를 보장해야 합니다.

### 2. 하위 호환성 관리를 위한 Versioning 전략
이미 대기 중이거나 진행 중인 Long-running 워크플로우가 있는 상태에서 배포가 일어나 코드가 변경되면 **Nondeterminism Error**가 발생할 수 있습니다.
* 워크플로우 조건문 변경 시 `workflow.patched("v2-migration-flag")` 구문을 사용하여 구버전 히스토리를 가진 워크플로우와 신버전 워크플로우가 안전하게 동시 실행될 수 있도록 제어해야 합니다.

### 3. Worker 스케일링 정책
Temporal Worker는 **완전한 Stateless 프로세스**입니다. 
* 따라서 Kubernetes(EKS) 환경에서 CPU/Memory 사용량 또는 Temporal의 Queue Backlog 지표를 기반으로 **HPA(Horizontal Pod Autoscaler)**를 적용하면 traffic surge 상황에서도 손쉽게 탄력적 확장이 가능합니다.

## OUTRO: 백엔드 아키텍처의 미래와 생산성 혁신

분산 시스템에서 데이터를 정확하게 관리하는 문제는 지난 10년간 백엔드 개발자들을 끊임없이 괴롭혀온 숙제였습니다. 

Temporal이 가져온 **Durable Execution** 패러다임은 이 문제를 **'인프라 및 런타임 레이어'**로 완벽히 격리시켰습니다. 개발자는 더 이상 네트워크 패킷 분실이나 DB 락 타임아웃 때문에 잠을 설칠 필요 없이, 순수한 비즈니스 로직에만 집중할 수 있게 되었습니다.

현재 구축 중인 백엔드 서비스의 비동기 메시징 흐름이 꼬여있거나, 복잡한 Saga 패턴으로 인해 개발 생산성이 떨어진다면 Temporal.io의 도입을 강력하게 검토해 보시기 바랍니다. 이는 단순한 도구의 변경이 아닌, 백엔드 개발 생산성의 패러다임 shift입니다.
