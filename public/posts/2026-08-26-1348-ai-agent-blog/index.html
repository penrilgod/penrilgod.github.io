    AWS 비용 $0에 도전하기: LocalStack과 Terraform으로 구축하는 로컬 클라우드 개발 환경

    2026년 8월 26일 · penrilgod

    📌 오늘 글의 3줄 요약

    • AWS 클라우드 비용 폭탄과 느린 배포 피드백 루프를 해결하기 위해 Docker 기반의 AWS 에뮬레이터인 LocalStack을 활용합니다.
    • Terraform의 Endpoint 설정을 로컬로 우회하여, 실제 클라우드 리소스를 생성하지 않고도 완벽한 IaC(Infrastructure as Code) 테스트 환경을 구축합니다.
    • Python boto3 라이브러리를 통해 로컬 가상 S3와 DynamoDB가 유기적으로 맞물려 작동하는 실전 데이터 파이프라인 검증 코드를 구현합니다.

    아키텍트의 고민: “아직도 테스트를 위해 AWS 리얼 리소스를 띄우십니까?”#

    20년 가까이 데이터 엔지니어링과 백엔드 아키텍처를 설계해 오면서, 수많은 개발 팀이 겪는 공통적인 고질병을 보아왔습니다. 바로 **“클라우드 인프라 개발 및 테스트 비용의 낭비”**와 **“지루하게 긴 피드백 루프”**입니다.

    코드 한 줄을 고치고, S3 버킷에 파일이 올라갔을 때 DynamoDB에 메타데이터가 정상적으로 기록되는지 확인하기 위해 git push를 하고, CI/CD가 돌기를 기다렸다가, AWS 콘솔을 새로고침하는 과정. 이 비효율적인 루틴은 개발자의 몰입을 방해할 뿐만 아니라, 실수로 고비용 리소스를 켜두었을 때 “비용 폭탄"이라는 부메랑으로 돌아옵니다.

    오늘 소개할 LocalStack과 Terraform의 조합은 이러한 개발 환경의 페인 포인트(Pain Point)를 완벽하게 해결해 줍니다. 단 1원의 비용도 쓰지 않고, 오프라인 환경에서도 운영 환경과 100% 동일한 AWS 토폴로지를 로컬 컴퓨터(Docker)에 1초 만에 프로비저닝하는 방법을 공유합니다.

    1. LocalStack과 Terraform의 시너지 메커니즘#

    LocalStack은 Docker 상에서 S3, Lambda, DynamoDB, SQS, SNS 등 핵심 AWS API를 에뮬레이션해 주는 강력한 가상 프레임워크입니다. 여기에 선언형 인프라 관리 도구인 Terraform이 결합하면 진가를 발휘합니다.

    [개발자 코드 (Python/boto3)] 
         │
         ▼ (http://localhost:4566)
┌─────────────────────────────────────────┐
│              LocalStack                 │
│  ┌──────────────┐      ┌─────────────┐  │
│  │  Virtual S3  │ ───> │ Virtual     │  │
│  │  Bucket      │      │ DynamoDB    │  │
│  └──────────────┘      └─────────────┘  │
└─────────────────────────────────────────┘
         ▲
         │ (Resource Provisioning)
[ Terraform (tflocal) ]

    핵심 메커니즘은 매우 간단합니다. Terraform의 AWS Provider 설정에서 AWS 실제 서비스 엔드포인트를 로컬 가상 컨테이너 주소(http://localhost:4566)로 리다이렉팅하는 것입니다. 이렇게 하면 인프라 코드를 수정하지 않고도 개발 환경에서는 로컬을 가리키고, 운영 환경에서는 실제 AWS를 가리키도록 유연하게 스위칭할 수 있습니다.

    2. 실전 로컬 클라우드 구축 3단계#

    그럼 실제로 로컬 개발 환경을 구축해 보겠습니다. S3에 원본 데이터가 업로드되면, 이를 감지하여 DynamoDB 테이블에 업로드 이력을 기록하는 시나리오를 설계합니다.

    Step 1. docker-compose.yml 작성#

    먼저 로컬에 AWS 에뮬레이터를 구동하기 위한 Docker Compose 파일을 생성합니다.

    version: "3.8"

services:
  localstack:
    container_name: localstack_main
    image: localstack/localstack:latest
    ports:
      - "127.0.0.1:4566:4566"            # LocalStack Edge Port
    environment:
      - SERVICES=s3,dynamodb,iam         # 활성화할 AWS 서비스 지정
      - AWS_DEFAULT_REGION=ap-northeast-2
      - DOCKER_HOST=unix:///var/run/docker.sock
    volumes:
      - "./localstack:/var/lib/localstack"
      - "/var/run/docker.sock:/var/run/docker.sock"

    터미널에서 docker compose up -d 명령어를 실행하여 컨테이너를 구동합니다.

    Step 2. Terraform 프로비저닝 설정#

    다음으로 로컬 인프라를 정의할 provider.tf와 main.tf를 구현합니다. 가상 엔드포인트(http://localhost:4566)를 바라보도록 바인딩하는 것이 핵심입니다.

    provider.tf#

    provider "aws" {
  access_key                  = "mock_access_key"
  secret_key                  = "mock_secret_key"
  region                      = "ap-northeast-2"
  s3_use_path_style           = true
  skip_credentials_validation = true
  skip_metadata_api_check     = true
  skip_requesting_account_id  = true

  # 모든 AWS 서비스 요청을 LocalStack Edge Port로 우회
  endpoints {
    s3       = "http://localhost:4566"
    dynamodb = "http://localhost:4566"
    iam      = "http://localhost:4566"
  }
}

    main.tf#

    # 로컬 테스트용 S3 버킷 생성
resource "aws_s3_bucket" "local_bucket" {
  bucket = "dev-data-lake-bucket"
}

# 로컬 테스트용 DynamoDB 테이블 생성
resource "aws_dynamodb_table" "local_metadata_table" {
  name         = "ImageMetadata"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "file_id"

  attribute {
    name = "file_id"
    type = "S3"
  }
}

    이제 해당 디렉토리에서 terraform init 후 terraform apply --auto-approve를 실행해 봅니다. 단 2초 만에 로컬 가상 머신 내부에 S3 버킷과 DynamoDB가 프로비저닝됩니다.

    Step 3. Python 애플리케이션 및 데이터 파이프라인 검증#

    인프라가 구성되었으니, 파이썬 백엔드 코드에서 이 로컬 리소스를 활용해 실제로 동작하는지 검증해 보겠습니다. boto3 클라이언트를 생성할 때 endpoint_url 파라미터를 LocalStack 주소로 전달하는 것이 유일한 차이점입니다.

    import os
import boto3
from botocore.exceptions import ClientError

# LocalStack 연결을 위한 엔드포인트 설정
LOCAL_ENDPOINT = "http://localhost:4566"

# boto3 클라이언트 생성 (로컬 환경일 때만 endpoint_url 적용)
s3_client = boto3.client(
    "s3",
    endpoint_url=LOCAL_ENDPOINT,
    aws_access_key_id="mock_access_key",
    aws_secret_access_key="mock_secret_key",
    region_name="ap-northeast-2"
)

dynamodb_resource = boto3.resource(
    "dynamodb",
    endpoint_url=LOCAL_ENDPOINT,
    aws_access_key_id="mock_access_key",
    aws_secret_access_key="mock_secret_key",
    region_name="ap-northeast-2"
)

def upload_and_log_metadata(bucket_name, table_name, file_path, file_key):
    """
    S3에 파일을 업로드하고, 성공 시 DynamoDB에 업로드 이력 메타데이터를 기록하는 함수
    """
    try:
        # 1. 가상 S3 버킷에 파일 업로드
        print(f"[*] S3 업로드 중: {file_path} -> s3://{bucket_name}/{file_key}")
        s3_client.upload_file(file_path, bucket_name, file_key)
        print("[+] S3 업로드 완료!")

        # 2. 가상 DynamoDB 테이블에 메타데이터 생성
        table = dynamodb_resource.Table(table_name)
        metadata = {
            "file_id": file_key,
            "status": "UPLOADED",
            "size_bytes": os.path.getsize(file_path),
            "created_at": "2026-08-26T13:48:41+09:00"
        }
        
        print(f"[*] DynamoDB 메타데이터 기록 중: {file_key}")
        table.put_item(Item=metadata)
        print("[+] DynamoDB 기록 성공!")
        
        # 3. 데이터 검증 (결과 조회)
        response = table.get_item(Key={"file_id": file_key})
        print(f" 확인된 데이터베이스 레코드: {response.get('Item')}")

    except ClientError as e:
        print(f"[-] 에러 발생: {e.response['Error']['Message']}")
    except Exception as e:
        print(f"[-] 일반 에러 발생: {str(e)}")

if __name__ == "__main__":
    # 임시 테스트용 파일 생성
    sample_file_path = "test_image.jpg"
    with open(sample_file_path, "wb") as f:
        f.write(b"fake_image_bytes_data")

    # 함수 실행
    upload_and_log_metadata(
        bucket_name="dev-data-lake-bucket",
        table_name="ImageMetadata",
        file_path=sample_file_path,
        file_key="user_uploads/test_image.jpg"
    )

    # 임시 파일 삭제
    if os.path.exists(sample_file_path):
        os.remove(sample_file_path)

    이 파이썬 스크립트를 터미널에서 실행해 보면, 실제 AWS 요금이 전혀 부과되지 않으면서도 로컬 콘솔 상에서 완벽히 성공하는 모습을 즉시 확인할 수 있습니다.

    3. CI/CD 파이프라인 통합 (GitHub Actions)#

    이 로컬 개발 가이드라인의 연장선으로, CI/CD 러너 가상 머신 환경 내에서도 LocalStack 서비스를 실행하여 PR(Pull Request) 단위의 클라우드 리소스 통합 테스트를 무료로 구현할 수 있습니다.

    name: LocalStack Integration Test

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Code
        uses: actions/checkout@v3

      # LocalStack을 백그라운드 서비스로 실행
      - name: Start LocalStack
        run: |
          docker compose up -d
          echo "Waiting for LocalStack to start..."
          sleep 10 # 서비스 안정화를 위한 대기 시간

      - name: Run Terraform Setup
        run: |
          terraform init
          terraform apply --auto-approve

      - name: Run Integration Tests
        run: |
          pip install boto3 pytest
          pytest tests/

    이를 통해 값비싼 AWS 리얼 환경을 계속 생성하고 파괴하는 번거로움과 리스크 없이, CI 파이프라인 내부에서 안정적이고 빠른 회귀 테스트 환경을 확보할 수 있습니다.

    💡 실무 적용 팁: 시니어 엔지니어가 전하는 3가지 조언#

    실무 프로젝트에서 LocalStack과 Terraform을 도입할 때 반드시 숙지해야 하는 현실적인 체크포인트입니다.

    1. tflocal 유틸리티 적극 활용 Terraform 파일 내에 엔드포인트 우회 설정을 하드코딩하기 번거롭다면, 오픈소스인 tflocal CLI를 활용해 보십시오. 실제 AWS 인프라 코드를 수정 없이 그대로 사용하면서, 커맨드라인 레벨에서 LocalStack으로 바인딩을 대행해 줍니다.
    2. 환경(Environment) 변수 분리 코드 내에 endpoint_url을 직접 명시하지 마십시오. 환경 변수로 STAGE=local 등을 인젝션받고, 로컬 단계일 때만 Python 팩토리 메서드에서 자동으로 로컬 엔드포인트를 할당해 주도록 추상화 패턴을 정립해야 운영 배포 시의 불상사를 피할 수 있습니다.
    3. 커뮤니티 버전의 한계 인지 기본적인 S3, DynamoDB, Lambda 등은 로컬스택 오픈소스(Free) 버전으로도 완벽히 커버됩니다. 하지만 Cognito, RDS(PostgreSQL 제외), EKS, Glue와 같은 엔터프라이즈 기능은 LocalStack Pro 라이선스가 필요할 수 있습니다. 비즈니스 규모에 맞춰 도입 타당성을 사전에 타진하는 것을 권장합니다.

    마치며#

    현대의 클라우드 개발 트렌드는 “빠른 피드백과 검증"이 핵심입니다. 개발자 한 명당 하나씩의 클라우드 계정을 제공하기 벅찬 비즈니스 상황에서, LocalStack과 Terraform의 조합은 인프라의 민주화를 실현해 줍니다.

    작은 환경 변수 분리 작업 하나가 개발 팀 전체의 생산성을 수십 배로 증대시키고, 한 달에 수천 달러씩 새어 나가던 개발계 클라우드 비용 청구서를 극적으로 다이어트시켜 줄 것입니다. 오늘 당장 여러분의 개발 머신 위에 나만의 작은 AWS 클라우드를 구축해 보시는 것은 어떨까요?
