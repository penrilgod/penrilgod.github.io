## 들어가며: Over-engineering에 지친 백엔드 개발자들에게

시니어 데이터 엔지니어로 근무하며 수많은 스타트업과 대기업의 클라우드 아키텍처를 검토해 왔습니다. 그 과정에서 가장 자주 목격하는 안타까운 광경 중 하나는 바로 **'과도한 인프라 구축(Over-engineering)'**입니다. 

이제 막 시작하는 MVP(최소 기능 제품) 단계이거나, 트래픽이 간헐적인 내부 서비스, 혹은 읽기(Read) 요청이 80% 이상을 차지하는 B2B SaaS에 월 50달러에서 150달러에 달하는 AWS RDS(관계형 데이터베이스 서비스)를 기본값으로 배치하는 경우가 너무나 많습니다. 

과거에는 데이터 유실 방지와 고가용성(HA)을 위해 RDS가 필수적인 선택지였을지 모릅니다. 하지만 최근 글로벌 오픈소스 생태계에서는 아주 흥미로운 패러다임 시프트가 일어나고 있습니다. 바로 가벼운 Go(Golang) 언어, 성능이 극대화된 **SQLite**, 그리고 실시간 스트리밍 복제 도구인 **Litestream**을 결합하여, 단돈 몇 달러(혹은 무료 티어)로 프로덕션 레디(Production-ready) 백엔드를 완성하는 아키텍처입니다.

오늘 글에서는 단순한 이론을 넘어, SQLite를 프로덕션 환경에서 쓸 수 있게 만드는 핵심 기술 요소와 이를 검증하는 방법, 그리고 실무 적용 노하우까지 깊이 있게 파헤쳐 보겠습니다.

## 1. SQLite의 재발견: 단순 토이 프로젝트용 DB가 아니다

많은 개발자들이 SQLite를 '테스트용 가벼운 DB' 혹은 '모바일 앱 내장용 임베디드 DB' 정도로 치부합니다. 그러나 SQLite는 현대적인 운영체제와 하드웨어 환경에서 놀라울 정도의 성능을 발휘합니다.

### 💡 WAL(Write-Ahead Logging) 모드의 마법
기본적으로 SQLite는 데이터 쓰기 작업을 할 때 데이터베이스 파일 전체에 락(Lock)을 걸어 동시성을 제한합니다. 하지만 **WAL(Write-Ahead Logging) 모드**를 활성화하면 이야기가 완전히 달라집니다.

* **동시 읽기/쓰기 가능**: 쓰기 트랜잭션이 수행되는 동안에도 읽기 트랜잭션이 블로킹되지 않고 동시에 실행됩니다.
* **디스크 I/O 최적화**: 변경 사항이 즉시 메인 데이터베이스 파일에 기록되는 대신, 메모리 버퍼와 매우 빠른 순차 쓰기 방식의 WAL 파일(`.db-wal`)에 먼저 기록됩니다. 이후 백그라운드에서 주기적으로 메인 DB 파일에 병합(Checkpointing)됩니다.
* **레이턴시 제로**: 네트워크 소켓 통신을 거쳐야 하는 PostgreSQL이나 MySQL과 달리, 애플리케이션과 동일한 프로세스 메모리 공간 및 로컬 디스크를 사용하므로 쿼리 레이턴시가 마이크로초(µs) 단위로 떨어집니다.

SQLite의 다중 스레드 동시성 성능이 프로덕션 환경에서 얼마나 버틸 수 있는지 의구심이 드는 분들을 위해, 파이썬(Python)의 `concurrent.futures`를 사용하여 대규모 동시성 쓰기/읽기 부하 테스트를 수행하는 시뮬레이션 코드를 준비했습니다. 이 코드는 실제 프로덕션 수준의 트래픽을 가정하여 WAL 모드 하에서 SQLite가 데드락 없이 안정적으로 작동함을 증명합니다.

```python
import sqlite3
import os
import time
import concurrent.futures

DB_FILE = "production_test.db"

def init_db():
    """데이터베이스 초기화 및 WAL 모드, busy_timeout 설정"""
    if os.path.exists(DB_FILE):
        os.remove(DB_FILE)
        
    conn = sqlite3.connect(DB_FILE)
    cursor = conn.cursor()
    # SQLite 핵심 최적화 설정
    cursor.execute("PRAGMA journal_mode=WAL;")      # WAL 모드 활성화
    cursor.execute("PRAGMA synchronous=NORMAL;")    # 디스크 동기화 최적화
    cursor.execute("PRAGMA busy_timeout=5000;")     # 대기 시간 5초로 설정 (락 방지)
    
    cursor.execute("""
        CREATE TABLE IF NOT EXISTS users (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            name TEXT NOT NULL,
            created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        )
    """)
    conn.commit()
    conn.close()
    print("[System] Database initialized with WAL mode.")

def simulate_write(worker_id):
    """동시 쓰기 시뮬레이션 (인서트 유저)"""
    conn = sqlite3.connect(DB_FILE)
    # 각 커넥션마다 busy_timeout 설정이 유지되어야 함
    conn.execute("PRAGMA busy_timeout=5000;")
    cursor = conn.cursor()
    
    try:
        for i in range(100):  # 워커당 100번 쓰기 시도
            cursor.execute("INSERT INTO users (name) VALUES (?)", (f"User_{worker_id}_{i}",))
            conn.commit()
            time.sleep(0.001)  # 마이크로 레이턴시 시뮬레이션
        return f"Worker {worker_id} successfully inserted 100 rows."
    except sqlite3.OperationalError as e:
        return f"Worker {worker_id} failed: {e}"
    finally:
        conn.close()

def simulate_read():
    """동시 읽기 시뮬레이션"""
    conn = sqlite3.connect(DB_FILE)
    cursor = conn.cursor()
    try:
        cursor.execute("SELECT COUNT(*) FROM users")
        count = cursor.fetchone()[0]
        return f"Current read count: {count}"
    finally:
        conn.close()

if __name__ == "__main__":
    init_db()
    
    start_time = time.time()
    # 20개의 스레드가 동시에 쓰기 작업을 수행 (컨커런시 극대화)
    with concurrent.futures.ThreadPoolExecutor(max_workers=20) as executor:
        # 쓰기 작업 스레드 제출
        write_futures = [executor.submit(simulate_write, i) for i in range(20)]
        
        # 중간중간 읽기 작업 병행 테스트 (WAL 모드의 동시성 증명)
        for _ in range(5):
            time.sleep(0.05)
            print(f"[Read Monitor] {simulate_read()}")
            
        # 모든 쓰기 완료 대기
        for future in concurrent.futures.as_completed(write_futures):
            print(f"[Write Result] {future.result()}")
            
    duration = time.time() - start_time
    print(f"\n[Summary] Total Execution Time: {duration:.2f} seconds")
    print(f"[Summary] Final Data Check: {simulate_read()}")
```

위 파이썬 스크립트를 실행해 보면, 20개의 스레드가 동시에 2,000번의 쓰기 트랜잭션을 몰아치는 상황에서도 단 한 건의 락오버플로우(Database is locked) 에러 없이 부드럽게 모든 트랜잭션이 완료됨을 확인할 수 있습니다. WAL 모드와 적절한 `busy_timeout` 조율만 있다면, 중소규모 트래픽 수준의 웹 애플리케이션 백엔드로 SQLite는 전혀 무리가 없습니다.

## 2. Litestream의 구동 메커니즘과 실시간 S3 동기화

SQLite의 가장 큰 약점은 무엇일까요? 바로 **"서버가 죽으면 데이터도 죽는다"**는 것입니다. 로컬 단일 파일로 저장이 되다 보니, EC2 인스턴스가 터지거나 가상 서버(VPS)가 삭제되면 데이터 복구가 불가능했습니다.

이 치명적인 한계를 우아하게 해결해 준 오픈소스 프로젝트가 바로 **Litestream**입니다.

```
┌──────────────────────────────────────┐
│       Go Application (Engine)        │
│   ┌──────────────────────────────┐   │
│   │        SQLite (.db)          │   │
│   └──────────────┬───────────────┘   │
│                  │ (Writes to)       │
│                  ▼                   │
│   ┌──────────────────────────────┐   │
│   │       WAL File (.db-wal)     │   │
│   └──────────────┬───────────────┘   │
└──────────────────┼───────────────────┘
                   │
                   │ (Intercepts WAL frames & streams)
                   ▼
┌──────────────────────────────────────┐
│             Litestream               │
└──────────────────┬───────────────────┘
                   │
                   │ (Secured S3 Upload)
                   ▼
┌──────────────────────────────────────┐
│      AWS S3 / Cloudflare R2          │
└──────────────────────────────────────┘
```

### 📋 Litestream의 작동 원리
1. **WAL 프레임 감시**: Litestream은 백그라운드 프로세스로 상주하면서 SQLite의 WAL 파일(`.db-wal`)을 초 단위 이하(Sub-second) 주기로 모니터링합니다.
2. **증분 복제(Incremental Replication)**: WAL 파일에 새로운 프레임(트랜잭션 데이터)이 작성될 때마다, 변경된 블록만 바이트 단위로 쪼개어 AWS S3, Cloudflare R2, 혹은 Backblaze B2 같은 오브젝트 스토리지에 실시간 스트리밍 형태로 전송합니다.
3. **스냅샷 병합**: 하루에 한 번 혹은 지정된 주기마다 데이터베이스의 전체 스냅샷을 다시 작성하여 S3 용량을 효율적으로 관리하고 복구 시간을 최소화합니다.

이 방식의 최고 장점은 애플리케이션 레이어의 수정을 전혀 요구하지 않는다는 것입니다. Go 백엔드는 평소대로 SQLite에 로컬 파일 쓰기만 수행하면 되고, 백업은 OS 레벨에서 Litestream이 독립적으로 완벽하게 보장합니다. 만약 VM이 통째로 삭제되더라도 `litestream restore` 명령 한 줄이면 S3에 저장되어 있던 최종 시점의 데이터베이스 파일이 그대로 재구성됩니다.

## 3. Go + SQLite + Litestream 실무 배포 아키텍처 가이드

그렇다면 실제 이 기술 스택을 활용하여 상용 배포 가능한 도커(Docker) 컨테이너 환경을 어떻게 구축할 수 있을까요? 시니어 개발자가 실무에서 직접 검증한 템플릿 구조를 소개합니다.

### 🧱 전체 파일 구조
```text
.
├── Dockerfile
├── entrypoint.sh
├── litestream.yml
├── go.mod
└── main.go
```

### 1단계: `litestream.yml` 설정 파일 정의
오브젝트 스토리지 경로와 복제할 SQLite 데이터베이스 파일 위치를 지정합니다.

```yaml
# litestream.yml
dbs:
  - path: /data/production.db
    replicas:
      - url: s3://your-s3-bucket-name/production.db
        sync-interval: 1s # 1초 간격 실시간 동기화
```

### 2단계: `entrypoint.sh` 셸 스크립트 구성
컨테이너가 기동될 때, 먼저 S3로부터 기존 백업본이 있는지 확인하여 데이터베이스를 복원(Restore)한 다음, Litestream 백그라운드 프로세스와 Go 웹 서버를 동시에 실행합니다.

```bash
#!/bin/sh
set -e

# S3로부터 기존 백업 파일 복원 시도 (존재하지 않으면 패스)
if [ -f /data/production.db ]; then
  echo "Local database already exists."
else
  echo "No local database found. Restoring from S3..."
  litestream restore -if-db-not-exists -if-replica-exists -config /etc/litestream.yml /data/production.db
fi

# Litestream을 백그라운드에서 실행하고 Go 바이너리 실행
exec litestream replicate -config /etc/litestream.yml -- /app/main
```

### 3단계: `Dockerfile` 작성 (멀티 스테이지 빌드)
컨테이너 이미지의 크기를 극한으로 줄이기 위해 Go 컴파일 단계와 배포 단계를 나눈 멀티 스테이지 방식을 도입하고, 공식 Litestream 배포판 이미지를 바이너리 형태로 복사해 옵니다.

```dockerfile
# ---------------------------------------------------
# Stage 1: Go Application Builder
# ---------------------------------------------------
FROM golang:1.21-alpine AS builder
RUN apk add --no-cache gcc musl-dev
WORKDIR /app
COPY go.mod ./
# SQLite 드라이버(CGO 사용)를 컴파일하기 위해 CGO_ENABLED=1 활성화
ENV CGO_ENABLED=1
COPY . .
RUN go build -ldflags="-w -s" -o main .

# ---------------------------------------------------
# Stage 2: Final Production Runner with Litestream
# ---------------------------------------------------
FROM alpine:3.18
RUN apk add --no-cache ca-certificates sqlite-libs

# Litestream 공식 이미지로부터 바이너리만 복사
COPY --from=litestream/litestream:0.3.13 /usr/local/bin/litestream /usr/local/bin/litestream

WORKDIR /app
COPY --from=builder /app/main /app/main
COPY litestream.yml /etc/litestream.yml
COPY entrypoint.sh /app/entrypoint.sh

RUN chmod +x /app/entrypoint.sh
RUN mkdir -p /data

# AWS 자격 증명 환경 변수 슬롯 제공 (ECS Task Role 또는 VPS 환경 변수 주입 필요)
ENV AWS_ACCESS_KEY_ID=""
ENV AWS_SECRET_ACCESS_KEY=""

EXPOSE 8080
ENTRYPOINT ["/app/entrypoint.sh"]
```

## 💡 실무 적용 팁

현업 아키텍처에 이 조합을 실제로 적용할 때, 놓치기 쉬운 세 가지 포인트를 데이터 엔지니어 관점에서 짚어드립니다.

* **S3 비용 최소화 (Life Cycle Policy 설정)**: Litestream은 많은 작은 파일 조각(WAL 프레임들)을 지속적으로 S3에 업로드합니다. S3 API 호출 비용이 부담될 수 있으므로, Cloudflare R2(API 호출 비용 100% 무료)를 결합하는 것이 궁극의 가성비 조합입니다.
* **`busy_timeout` 설정은 필수**: SQLite를 동시성 환경에서 쓸 때 `busy_timeout` 설정을 누락하면 약간의 쓰기 경쟁이 발생해도 즉시 `database is locked` 오류를 뿜어냅니다. Go DB 커넥션 스트링을 작성할 때 반드시 `_busy_timeout=5000`을 추가하십시오.
* **쓰기 집약적(Write-heavy) 서비스 피하기**: 초당 수천 건의 로그 수집기나, 주식 호가 데이터 적재 등 지속적인 쓰기 작업이 메인 도메인인 서비스에는 여전히 PostgreSQL이나 TimescaleDB가 훨씬 좋은 대안입니다. 이 아키텍처는 **웹 비즈니스 로직(CRUD)과 대시보드형 서비스**에 최적화되어 있습니다.

## 마치며: 스마트한 시니어 개발자의 무기, "단순함"

비즈니스의 핵심은 '빠른 고객 피드백 루프'와 '비용 효율성'입니다. 무조건 트렌디한 MSA(마이크로서비스 아키텍처)나 무거운 분산 DB를 도입하여 인프라 비용과 관리 복잡성을 늘리는 것은 개발 초기 단계에서 패착이 될 수 있습니다.

**Go + SQLite + Litestream** 조합은 **월 5달러짜리 가장 저렴한 리눅스 서버 하나와 거의 무료에 가까운 S3 용량**만으로도, 초당 수천 개의 요청을 레이턴시 없이 거뜬히 처리하는 가성비 극대화 구조를 제공합니다. 단순하면서도 견고한 무기를 가방에 챙겨 두고, 적재적소에 꺼내 드는 것이 진정한 시니어 개발자의 가치입니다. 오늘 당장 여러분의 사이드 프로젝트나 사내 MVP 아키텍처를 이 무기를 활용해 리팩토링해 보시는 것은 어떨까요?
