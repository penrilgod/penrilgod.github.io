    Elasticsearch 없이 구축하는 고성능 하이브리드 검색 엔진: PostgreSQL과 pgvector(HNSW) + RRF 실전 가이드

    2026년 9월 11일 · penrilgod

    📌 오늘 글의 3줄 요약

    • 인프라 단순화: 전용 Vector DB 도입으로 인한 데이터 동기화 지연과 비용 문제를 PostgreSQL pgvector로 완전히 해결할 수 있습니다.
    • HNSW 인덱싱: pgvector 0.5.0 이상에서 지원하는 HNSW 인덱스를 활용하여 밀리초(ms) 단위의 고성능 벡터 유사도 검색을 구현합니다.
    • 하이브리드 검색 최적화: Full-Text Search(BM25 기반)와 Vector Search의 결과를 단일 SQL 내에서 RRF(Reciprocal Rank Fusion) 알고리즘으로 병합하여 검색 정확도를 극대화합니다.

    시작하며: 왜 대기업들은 벡터 전용 DB에서 PostgreSQL로 회귀할까?#

    최근 LLM(대형 언어 모델)을 결합한 RAG(Retrieval-Augmented Generation) 시스템이나 시맨틱(Semantic) 검색 서비스 구축이 엔터프라이즈의 필수 과제가 되었습니다. 초기 시장에서는 Pinecone, Milvus, Qdrant 등 ‘벡터 전용 데이터베이스’가 큰 주목을 받았습니다.

    하지만 실제 프로덕션 환경에서 운영해 본 많은 데이터 엔지니어들은 곧 커다란 장벽에 부딪히게 되었습니다.

    1. 데이터 정합성(ACID) 보장의 한계: 관계형 데이터(사용자 정보, 주문 상태, 재고 등)와 벡터 데이터를 서로 다른 DB에 저장하면서 발생하는 데이터 동기화 지연.
    2. 인프라 관리 복잡성 및 비용: 별도의 DB 서버 유지 보수, 네트워크 레이턴시 증가, 그리고 이중 지출되는 인프라 비용.
    3. 복잡한 메타데이터 필터링: “재고가 있고, 서울 지역 배송이 가능하며, 특정 가격 이하인” 상품 중 유사 벡터를 찾는 복잡한 하이브리드 쿼리의 성능 저하.

    이러한 문제를 해결하기 위해 최근 실무 진영에서는 PostgreSQL을 활용한 싱글 DB 아키텍처로 빠르게 회귀하고 있습니다. PostgreSQL의 확장 프레임워크인 pgvector가 진화하면서, 이제는 전용 Vector DB 못지않은 성능을 RDBMS의 강력한 ACID 트랜잭션 안에서 그대로 누릴 수 있게 되었기 때문입니다.

    이번 가이드에서는 PostgreSQL을 활용해 형태소 분석 기반의 키워드 검색(FTS)과 고차원 벡터 임베딩 검색을 결합하고, 이를 RRF(Reciprocal Rank Fusion) 알고리즘으로 랭킹화하는 고성능 하이브리드 검색 엔진을 밑바닥부터 구현해 보겠습니다.

    Step 1. PostgreSQL에 pgvector 탑재 및 테이블 설계#

    먼저 pgvector 모듈이 포함된 PostgreSQL 환경을 Docker로 구동해 보겠습니다. 오픈소스 커뮤니티에서 가장 널리 쓰이는 ankane/pgvector 이미지를 활용합니다.

    # pgvector가 사전 설치된 PostgreSQL 컨테이너 실행
docker run -d \
  --name postgres-vector \
  -e POSTGRES_DB=search_db \
  -e POSTGRES_USER=admin \
  -e POSTGRES_PASSWORD=secret_password \
  -p 5432:5432 \
  pgvector/pgvector:pg16

    이제 데이터베이스에 접속하여 pgvector 익스텐션을 활성화하고, 이커머스 상품 데이터를 담을 테이블을 설계합니다. 여기서는 OpenAI의 text-embedding-3-small 모델이 생성하는 1536 차원의 벡터를 기준으로 삼겠습니다.

    -- 1. pgvector 익스텐션 활성화
CREATE EXTENSION IF NOT EXISTS vector;

-- 2. 상품 테이블 생성 (키워드 검색용 tsvector와 벡터 검색용 vector 타입 포함)
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    description TEXT NOT NULL,
    price NUMERIC(10, 2) NOT NULL,
    status VARCHAR(50) DEFAULT 'IN_STOCK',
    -- 형태소 분석 및 키워드 검색 속도 향상을 위한 tsvector 필드
    fts_tokens TSVECTOR GENERATED ALWAYS AS (
        to_tsvector('english', title || ' ' || description)
    ) STORED,
    -- 1536 차원의 고밀도 벡터 필드
    embedding VECTOR(1536)
);

    Step 2. 성능 극대화를 위한 HNSW(Hierarchical Navigable Small World) 인덱스 튜닝#

    pgvector는 크게 IVFFlat과 HNSW 두 가지 인덱스 유형을 제공합니다.

    인덱스 종류빌드 시간쿼리 응답 속도메모리 오버헤드리콜률 (정확도)
    IVFFlat빠름보통매우 적음보통 (데이터 업데이트 시 저하)
    HNSW느림매우 빠름높음매우 높음 (안정적)

    실무 프로덕션 환경에서는 쿼리 레이턴시가 가장 중요하므로, HNSW 인덱스를 적극 권장합니다. HNSW는 다층 그래프 구조를 생성하여 근사 최근접 이웃(ANN)을 탐색하므로, 데이터가 추가/변경되어도 리콜률이 쉽게 깨지지 않습니다.

    -- HNSW 인덱스 생성 (코사인 유사도 연산자 기준)
CREATE INDEX idx_products_hnsw_embedding ON products 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);
    • m (최대 연결 수): 그래프의 각 노드가 가질 수 있는 양방향 링크의 최대 개수입니다. 값이 클수록 리콜률이 높아지지만 인덱스 빌드 시간과 메모리 사용량이 늘어납니다. (추천 범위: 16 ~ 64)
    • ef_construction (탐색 범위): 인덱스를 빌드할 때 탐색할 인접 노드의 수입니다. 이 값을 높이면 빌드 시간은 늘어나지만 인덱스 품질(정확도)이 비약적으로 상승합니다. (추천 범위: 64 ~ 512)

    Step 3. 하이브리드 검색(Hybrid Search) 쿼리 작성하기#

    단순한 키워드 검색(BM25 대용 FTS)이나 벡터 검색 하나만으로는 사용자의 다양한 의도를 백포센트 충족하기 어렵습니다.

    • 키워드 검색: “바람막이”, “Nike"와 같은 명확한 고유 명사나 품번 검색에 탁월합니다.
    • 벡터 검색: “비 올 때 입는 가벼운 검은색 아우터"처럼 의미적 유사도(Semantic)를 판단하는 데 적합합니다.

    이 두 가지를 병합하기 위해, 먼저 각 영역의 원시 쿼리를 살펴보겠습니다.

    -- 1. 키워드 검색 쿼리 (FTS)
SELECT id, title, ts_rank_cd(fts_tokens, query) as keyword_rank
FROM products, websearch_to_tsquery('english', 'waterproof windbreaker') query
WHERE fts_tokens @@ query
ORDER BY keyword_rank DESC
LIMIT 50;

-- 2. 벡터 검색 쿼리 (Cosine Distance, '<=>' 연산자 활용)
-- pgvector에서 '<=>'는 코사인 거리를 뜻하므로, 0에 가까울수록 유사도가 높습니다.
SELECT id, title, (1 - (embedding <=> '[0.012, -0.023, ...1536차원 벡터]')) as cosine_similarity
FROM products
ORDER BY embedding <=> '[0.012, -0.023, ...1536차원 벡터]'
LIMIT 50;

    Step 4. RRF(Reciprocal Rank Fusion) 알고리즘을 SQL로 구현하기#

    두 검색 엔진의 원시 점수(Score)는 단위가 다릅니다. 키워드 랭크 점수는 최대 제한이 없는 반면, 코사인 유사도는 0과 1 사이의 값입니다. 이를 단순히 더하거나 곱하면 한쪽 검색 결과에 왜곡이 생깁니다.

    이때 활용하는 표준 알고리즘이 바로 **RRF(Reciprocal Rank Fusion)**입니다. RRF는 점수 자체가 아니라 **‘결과 목록에서의 순위(Rank)’**를 역수로 취해 합산하는 방식입니다.

    $$\text{RRF Score} = \sum_{m \in M} \frac{1}{k + r_m(d)}$$

    여기서 $r_m(d)$는 모델 $m$이 문서 $d$에 매긴 순위이고, $k$는 상수(일반적으로 60)로 낮은 순위에 과도한 페널티가 부여되는 것을 방지합니다.

    이 복잡해 보이는 연산을 PostgreSQL의 CTE(Common Table Expressions)와 Window Function을 이용해 외부 데이터 가공 없이 SQL 단 한 번의 쿼리로 처리할 수 있습니다.

    WITH keyword_search AS (
    SELECT 
        id, 
        ROW_NUMBER() OVER (ORDER BY ts_rank_cd(fts_tokens, websearch_to_tsquery('english', 'waterproof windbreaker')) DESC) as rank
    FROM products
    WHERE fts_tokens @@ websearch_to_tsquery('english', 'waterproof windbreaker')
    LIMIT 50
),
vector_search AS (
    SELECT 
        id, 
        ROW_NUMBER() OVER (ORDER BY embedding <=> %s::vector) as rank
    FROM products
    ORDER BY embedding <=> %s::vector
    LIMIT 50
)
SELECT 
    COALESCE(k.id, v.id) as product_id,
    p.title,
    p.price,
    -- RRF 점수 계산 (k = 60 설정)
    COALESCE(1.0 / (60 + k.rank), 0.0) + COALESCE(1.0 / (60 + v.rank), 0.0) as rrf_score
FROM keyword_search k
FULL OUTER JOIN vector_search v ON k.id = v.id
JOIN products p ON p.id = COALESCE(k.id, v.id)
ORDER BY rrf_score DESC
LIMIT 10;

    🐍 실전 파이썬 구동 예제 코드#

    다음은 Python의 psycopg2와 numpy를 활용하여 실제로 데이터베이스에 가상의 벡터를 삽입하고, 앞서 설계한 RRF 하이브리드 검색을 수행하는 완전한 동작 코드 예제입니다.

    import random
import psycopg2
from psycopg2.extras import execute_values


def get_connection():
    return psycopg2.connect(
        host="localhost",
        database="search_db",
        user="admin",
        password="secret_password",
        port=5432,
    )


def generate_mock_vector(dim=1536):
    """임의의 L2 정규화된 고차원 벡터 생성"""
    vec = [random.uniform(-1, 1) for _ in range(dim)]
    norm = sum(x**2 for x in vec) ** 0.5
    return [x / norm for x in vec]


def insert_mock_data():
    conn = get_connection()
    cur = conn.cursor()

    # 샘플 상품 데이터 정의
    sample_products = [
        (
            "Waterproof Windbreaker Jacket",
            "High performance black waterproof windbreaker jacket for heavy rain and outdoor sports.",
            99.00,
        ),
        (
            "Lightweight Running Shoes",
            "Comfortable and breathable mesh running shoes with ultimate grip.",
            120.00,
        ),
        (
            "Heavy Winter Down Jacket",
            "Keep warm with this goose down feather extreme cold winter jacket.",
            250.00,
        ),
        (
            "Casual Cotton Black T-Shirt",
            "Simple minimalist black t-shirt made of 100% premium cotton.",
            29.00,
        ),
    ]

    data_to_insert = []
    for title, desc, price in sample_products:
        # 실제 환경에서는 OpenAI text-embedding-3-small API 결과물을 대입합니다.
        embedding = generate_mock_vector(1536)
        data_to_insert.append((title, desc, price, embedding))

    # 데이터 벌크 삽입
    query = """
        INSERT INTO products (title, description, price, embedding) 
        VALUES %s
    """
    execute_values(cur, query, data_to_insert)
    conn.commit()
    print(f"Successfully inserted {len(sample_products)} items.")
    cur.close()
    conn.close()


def run_hybrid_search(search_query: str, query_vector: list):
    conn = get_connection()
    cur = conn.cursor()

    rrf_sql = """
    WITH keyword_search AS (
        SELECT 
            id, 
            ROW_NUMBER() OVER (ORDER BY ts_rank_cd(fts_tokens, websearch_to_tsquery('english', %s)) DESC) as rank
        FROM products
        WHERE fts_tokens @@ websearch_to_tsquery('english', %s)
        LIMIT 50
    ),
    vector_search AS (
        SELECT 
            id, 
            ROW_NUMBER() OVER (ORDER BY embedding <=> %s::vector) as rank
        FROM products
        ORDER BY embedding <=> %s::vector
        LIMIT 50
    )
    SELECT 
        COALESCE(k.id, v.id) as product_id,
        p.title,
        p.price,
        COALESCE(1.0 / (60 + k.rank), 0.0) + COALESCE(1.0 / (60 + v.rank), 0.0) as rrf_score
    FROM keyword_search k
    FULL OUTER JOIN vector_search v ON k.id = v.id
    JOIN products p ON p.id = COALESCE(k.id, v.id)
    ORDER BY rrf_score DESC
    LIMIT 5;
    """

    # 쿼리 파라미터 전달 (vector는 파이썬 리스트 형태로 그대로 전달 가능)
    cur.execute(
        rrf_sql, (search_query, search_query, query_vector, query_vector)
    )
    results = cur.fetchall()

    print(f"\n--- Search Results for: '{search_query}' ---")
    for row in results:
        print(
            f"[ID: {row[0]}] {row[1]:<35} | Price: ${row[2]:<6} | RRF Score: {row[3]:.5f}"
        )

    cur.close()
    conn.close()


if __name__ == "__main__":
    # 1. 테스트용 모크 데이터 삽입 (최초 1회 실행)
    insert_mock_data()

    # 2. 하이브리드 검색 시뮬레이션
    search_keyword = "black waterproof jacket"
    # 실제로는 유저 검색어(search_keyword)를 OpenAI 임베딩 API에 통과시켜 얻은 벡터를 넣습니다.
    target_vector = generate_mock_vector(1536)

    run_hybrid_search(search_keyword, target_vector)

    💡 시니어 엔지니어가 전하는 실무 적용 팁#

    현업 대용량 서비스 환경에서 PostgreSQL로 하이브리드 검색 엔진을 구축할 때는 반드시 다음 사항들을 준수해야 장애를 예방할 수 있습니다.

    1. 인덱스 메모리 타겟팅 (shared_buffers) HNSW 인덱스는 디스크가 아닌 메모리에 전부 적재되어 동작할 때 진정한 성능(서브 밀리초)이 나옵니다. 벡터의 차원과 개수를 고려하여 인덱스 파일 크기를 산출한 후, 시스템의 shared_buffers와 work_mem이 인덱스 전체를 담을 수 있을 만큼 충분한지 모니터링해야 합니다. (예: 1536 차원 Float32 벡터 100만 개 기준, 순수 벡터 데이터 크기만 약 6GB에 달합니다.)

    2. 인덱스 빌드 시 리소스 락(Lock) 방지 CREATE INDEX ... USING hnsw 연산은 CPU와 RAM을 매우 많이 소모합니다. 라이브 서비스 중인 DB에서 이 명령을 직접 내리면 DB가 응답 불능 상태에 빠질 수 있습니다. 반드시 CONCURRENTLY 옵션을 주어 백그라운드에서 안전하게 인덱스를 빌드하도록 조치하세요.

      CREATE INDEX CONCURRENTLY idx_products_hnsw_embedding ...

    3. RRF 상수 $k$ 조율 RRF 수식에서 $k$ 값은 시스템의 편향(Bias)을 조정하는 매우 중요한 파라미터입니다. $k$가 너무 작으면 상위 1, 2위에 선정된 특정 알고리즘의 편향이 지나치게 강해지고, $k$가 너무 크면 순위 차이로 인한 변별력이 약해집니다. 일반적으로 60이 업계 표준이지만, 자체 정답 셋(Ground Truth)이 존재한다면 최적화를 위해 $k$ 값을 30에서 100 사이로 그리드 서치(Grid Search)해 볼 필요가 있습니다.

    결론: 단순한 것이 복잡한 것을 이깁니다#

    Elasticsearch나 엔터프라이즈급 벡터 전용 DB 솔루션은 수천만 건 이상의 초대형 데이터셋과 고빈도 트래픽 환경에서 제 가치를 발휘합니다. 하지만 대다수의 초기 스타트업이나 중소형 미디엄 서비스(데이터 수백만 건 이하)에서는 과도한 엔지니어링 오버헤드를 유발할 확률이 매우 높습니다.

    PostgreSQL과 pgvector 기반의 하이브리드 검색 아키텍처는 단일 데이터베이스 내에서 완벽한 ACID 정합성을 지키면서도 레이턴시와 비용 측면에서 압도적인 효율을 자랑합니다. 인프라의 복잡성에 에너지를 낭비하기보다, 단순하지만 견고한 PostgreSQL 기반 아키텍처를 도입하여 비즈니스 가치를 빠르게 검증해 보시길 권장합니다.
