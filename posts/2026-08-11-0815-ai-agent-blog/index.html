    서론: 20년 차 엔지니어가 바라본 ‘오버 엔지니어링’의 덫#

    안녕하세요. 20년 동안 수많은 엔터프라이즈 데이터 플랫폼과 분산 백엔드 시스템을 설계해 온 시니어 데이터 엔지니어입니다.

    그동안 업계에서 새로운 서비스나 스타트업 프로젝트를 시작할 때, 묻지도 따지지도 않고 AWS RDS의 PostgreSQL이나 MySQL을 프로비저닝하는 광경을 수없이 목격했습니다. “언젠가 트래픽이 몰릴 테니까”, “안정성이 중요하니까"라는 명목하에 말이죠. 하지만 냉정하게 자문해 보아야 합니다. 진짜 서비스 극초기부터 초당 수만 건의 동시 쓰기가 발생하나요?

    현실은 다릅니다. 대부분의 서비스는 일일 활성 사용자(DAU) 수만 명 수준에 도달하는 데도 상당한 시간이 걸립니다. 그 과정에서 발생하는 월 수십~수백 달러의 데이터베이스 고정 비용, VPC 피어링, 서브넷 설정, PgBouncer 커넥션 풀링 관리 등은 초기 개발팀의 생산성을 좀먹는 ‘오버 엔지니어링’이 되기 십상입니다.

    이러한 고정 관념을 깨고 최근 **‘SQLite의 서버 사이드 회귀’**가 강력한 트렌드로 부상하고 있습니다. 그리고 이 흐름의 치트키가 바로 **Litestream(라이트스트림)**입니다. 오늘 본론에서는 SQLite와 Litestream을 조합하여 프로덕션 등급의 초경량·고성능 백엔드를 구축하는 실전 가이드를 깊이 있게 풀어보겠습니다.

    본론 1: 왜 SQLite + Litestream 조합인가?#

    1. SQLite의 재발견: 네트워크 레이턴시 ‘0ms’의 기적#

    전통적인 클라이언트-서버 데이터베이스(PostgreSQL 등)는 애플리케이션 서버와 데이터베이스 서버 간에 네트워크 통신(TCP/IP)을 합니다. 아무리 같은 리전에 묶어두어도 수 밀리초(ms)의 네트워크 레이턴시가 발생합니다.

    반면, SQLite는 애플리케이션의 프로세스 메모리 내부 혹은 로컬 디스크 상에서 직접 구동됩니다. 즉, 데이터베이스를 조회할 때 네트워크 홉(Hop)이 전혀 없어 쿼리 속도가 인메모리 DB 수준으로 빠릅니다.

    2. Litestream이 해결한 결정적 한계#

    SQLite의 가장 큰 단점은 **“서버 인스턴스가 날아가면 데이터도 날아간다”**는 점이었습니다. stateless한 클라우드 컨테이너 환경(Docker, Fly.io, AWS ECS 등)에서 SQLite를 함부로 쓰지 못했던 이유가 바로 여기에 있습니다.

    Litestream은 SQLite의 WAL(Write-Ahead Log) 메커니즘을 후킹하여 이 문제를 해결합니다.

    • SQLite에 데이터가 쓰일 때마다 생성되는 WAL 프레임을 백그라운드에서 감시합니다.
    • 변경된 데이터를 S3나 Cloudflare R2 같은 오브젝트 스토리지로 1초 미만의 주기로 실시간 스트리밍 복제합니다.
    • 서버 장애 발생 시, 단 한 줄의 명령어로 오브젝트 스토리지에서 최신 상태의 .db 파일을 완벽하게 복구(Restore)합니다.

    본론 2: FastAPI + SQLite + Litestream 실무 파이썬 구현#

    이제 실제로 구동 가능한 파이썬(FastAPI) 기반의 백엔드 코드와 Litestream 설정, 그리고 Docker 패키징까지 단계별로 살펴보겠습니다. 이 코드는 상용 환경에서 작동하도록 최적화된 설계 파일입니다.

    1. FastAPI 애플리케이션 코드 (app/main.py)#

    SQLite의 동시성 성능을 극대화하기 위해 WAL(Write-Ahead Log) 모드를 활성화하고, 커넥션 타임아웃을 최적화한 실무용 코드입니다.

    import os
import sqlite3
from contextlib import asynccontextmanager
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

DB_PATH = os.getenv("DATABASE_PATH", "/app/data/production.db")

def init_db():
    """데이터베이스 연결 초기화 및 WAL 모드 설정"""
    # 디렉토리가 없으면 생성
    os.makedirs(os.path.dirname(DB_PATH), exist_ok=True)
    
    conn = sqlite3.connect(DB_PATH, timeout=10.0)
    cursor = conn.cursor()
    
    # SQLite 성능 최적화를 위한 Pragma 설정
    cursor.execute("PRAGMA journal_mode=WAL;")  # 동시 읽기/쓰기 성능 대폭 향상
    cursor.execute("PRAGMA synchronous=NORMAL;") # 디스크 동기화 최적화
    cursor.execute("PRAGMA busy_timeout=10000;") # 락 대기 시간 설정 (10초)
    
    # 예제 테이블 생성
    cursor.execute("""
        CREATE TABLE IF NOT EXISTS users (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            username TEXT UNIQUE NOT NULL,
            email TEXT NOT NULL
        )
    """)
    conn.commit()
    conn.close()

@asynccontextmanager
async def lifespan(app: FastAPI):
    # 스타트업 시점에 DB 초기화
    init_db()
    yield
    # 클린업 동작이 필요하면 여기에 작성

app = FastAPI(title="SQLite-Litestream API Server", lifespan=lifespan)

class UserCreate(BaseModel):
    username: str
    email: str

@app.post("/users")
def create_user(user: UserCreate):
    conn = sqlite3.connect(DB_PATH, timeout=10.0)
    cursor = conn.cursor()
    try:
        cursor.execute(
            "INSERT INTO users (username, email) VALUES (?, ?)", 
            (user.username, user.email)
        )
        conn.commit()
        user_id = cursor.lastrowid
        return {"id": user_id, "username": user.username, "email": user.email}
    except sqlite3.IntegrityError:
        raise HTTPException(status_code=400, detail="Username already exists")
    finally:
        conn.close()

@app.get("/users/{user_id}")
def get_user(user_id: int):
    conn = sqlite3.connect(DB_PATH, timeout=10.0)
    cursor = conn.cursor()
    cursor.execute("SELECT id, username, email FROM users WHERE id = ?", (user_id,))
    row = cursor.fetchone()
    conn.close()
    
    if not row:
        raise HTTPException(status_code=404, detail="User not found")
    return {"id": row[0], "username": row[1], "email": row[2]}

    2. Litestream 설정 파일 (etc/litestream.yml)#

    데이터베이스 파일을 어디로 복제할지 정의하는 설정 파일입니다. Cloudflare R2 또는 AWS S3 호환 스토리지를 타겟으로 삼습니다.

    # /etc/litestream.yml
dbs:
  - path: /app/data/production.db
    replicas:
      - url: s3://my-sqlite-backup-bucket/production
        # Cloudflare R2 또는 AWS S3 자격 증명은 환경 변수로 주입받습니다.
        # AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, LIFESTREAM_ENDPOINT 등

    3. 컨테이너 엔트리포인트 스크립트 (entrypoint.sh)#

    서버가 뜰 때 백업을 복구하고, Litestream과 FastAPI를 멀티프로세스로 동시에 올리는 핵심 스크립트입니다.

    #!/bin/sh
set -e

# 1. 스토리지로부터 기존 백업 확인 및 자동 복구 (DB 파일이 없을 때만 수행)
if [ -f "/app/data/production.db" ]; then
    echo "Database already exists. Skipping restore."
else
    echo "No database found. Attempting to restore from Replica..."
    # 복구 실패해도 애플리케이션 실행을 위해 -if-replica-exists 옵션 부여
    litestream restore -if-db-not-exists -if-replica-exists /app/data/production.db
fi

# 2. Litestream 백그라운드 프로세스로 띄워 WAL 스트리밍 감시 후 FastAPI(Uvicorn) 구동
echo "Starting Litestream replication and FastAPI server..."
exec litestream replicate -exec "uvicorn app.main:app --host 0.0.0.0 --port 8080"

    본론 3: 실무에서 마주칠 트레이드오프와 튜닝 포인트#

    아무리 좋은 기술이라도 만병통치약은 없습니다. 20년 차 엔지니어로서 냉정하게 분석한 본 아키텍처의 한계와 극복 방법입니다.

    • 동시 쓰기 트래픽의 한계 (database is locked):
      • SQLite는 단일 라이터(Single Writer) 모델입니다. 동시 다발적인 대량의 쓰기 트랜잭션이 들어오면 대기 현상이 발생하며 database is locked 에러를 뱉을 수 있습니다.
      • 해결책: 위의 파이썬 코드처럼 timeout=10.0 (10초 대기)을 설정하고, 반드시 PRAGMA journal_mode=WAL;을 켜주어야 합니다. WAL 모드를 켜면 읽기 작업은 쓰기 작업을 블로킹하지 않아 웬만한 중소형 서비스(초당 수백 건의 트랜잭션)는 무리 없이 소화합니다.
    • 수평 확장(Horizontal Scale-out) 불가:
      • 애플리케이션 서버 인스턴스를 3대, 5대로 늘리게 되면 각각의 인스턴스가 독립적인 SQLite를 갖게 되므로 데이터 정합성이 깨집니다.
      • 해결책: 이 아키텍처는 단일 거대 인스턴스(Scale-up) 전략에 적합합니다. 최근 클라우드 VM은 1대에 수십 코어, 수백 GB RAM을 저렴하게 제공하므로 단일 노드로도 훌륭히 버틸 수 있습니다. 만약 멀티 노드 스케일아웃이 강제된다면, Litestream 대신 분산 합의 알고리즘을 쓰는 LiteFS 도입을 검토해야 합니다.

    💡 실무 적용 팁#

    실제 상용 서비스에 이 아키텍처를 도입할 때 시니어 엔지니어로서 권장하는 체크리스트 3가지입니다.

    1. 오브젝트 스토리지 비용 극대화하기:
      • AWS S3 대신 Cloudflare R2를 사용하세요. R2는 아웃바운드 데이터 전송료(Egress Fee)가 완전히 무료입니다. Litestream이 지속적으로 WAL 조각을 올릴 때 발생하는 네트워크 비용 부담이 제로에 가까워집니다.
    2. 백업 모니터링 구축:
      • Litestream은 프로메테우스(Prometheus) 메트릭 포트(-addr=:9090)를 자체 지원합니다. 복제 지연 시간(Replication Lag)이나 업로드 에러를 모니터링 시스템과 연동해 경고 알림을 설정하세요.
    3. 스키마 마이그레이션:
      • Alembic이나 DB 마이그레이션 도구를 적용할 때, 마이그레이션 중 발생하는 쓰기 락 타임아웃을 방지하기 위해 사용자가 가장 적은 시간대에 순차적으로 진행하는 스크립트를 빌드 파이프라인에 이식해야 합니다.

    결론: 아키텍처 단순화의 미학#

    개발자로서 가장 경계해야 할 태도는 “남들이 다 쓰니까 우리도 써야 한다"는 기술적 종속입니다. PostgreSQL, MySQL, 그리고 Kubernetes는 훌륭한 도구이지만, 제품 개발 극초기 단계에서 연간 수백만 원의 비용과 수많은 주말 장애 대응을 유발하는 원흉이 되기도 합니다.

    SQLite + Litestream 아키텍처는 단순함(Simplicity)과 가성비, 그리고 성능이라는 세 마리 토끼를 모두 잡을 수 있는 현대 백엔드 디자인의 정수입니다.

    “Simple is Beautiful.” 여러분의 다음 마이크로서비스나 스타트업 비즈니스는 비싸고 무거운 RDS 대신, 디스크 상에서 빛의 속도로 도는 SQLite와 든든한 보험 같은 Litestream의 조합으로 가볍고 탄탄하게 시작해 보시는 건 어떨까요?
