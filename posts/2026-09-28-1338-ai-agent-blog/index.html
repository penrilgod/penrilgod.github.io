    CloudFormation은 이제 안녕: SST Ion과 Pulumi로 구축하는 10배 빠른 AWS 서버리스(Serverless) 인프라

    2026년 9월 28일 · penrilgod

    📌 오늘 글의 3줄 요약

    • 속도의 한계 극복: 기존 AWS CDK와 Serverless Framework의 병목이었던 CloudFormation을 걷어내고, Pulumi 기반의 **SST Ion(v3)**으로 패러다임이 전환되고 있습니다.
    • 배포 속도 10배 개선: 무거운 CloudFormation 스택 업데이트 대신, 엔진 레벨에서 AWS API를 직접 호출하여 리소스 프로비저닝 시간을 분 단위에서 초 단위로 단축합니다.
    • 실무형 파이프라인 구현: 본 가이드에서는 SST Ion 환경에서 동작하는 고성능 S3 이벤트 기반 이미지 메타데이터 추출 Python Lambda 핸들러 실전 코드를 제공합니다.

    서론: “배포 버튼을 누르고 커피를 마시러 가던 시대는 끝났다”#

    클라우드 엔지니어 및 백엔드 개발자라면 누구나 한 번쯤 경험해 보았을 고통이 있습니다. 바로 IaC(Infrastructure as Code) 배포 대기 시간입니다.

    AWS CDK나 기존 Serverless Framework(v2 이하)는 개발자가 작성한 코드를 최종적으로 AWS CloudFormation(CFN) 템플릿(JSON/YAML)으로 변환하여 AWS에 전달합니다. 이 방식은 안전하지만 치명적인 단점이 있습니다. 단순한 API Gateway의 경로 하나를 수정하거나, Lambda 환경 변수 하나를 바꾸는 데도 수 분에서 십수 분에 이르는 트랜잭션 대기 시간이 소요된다는 점입니다. 개발 생태계에서 피드백 루프가 느려지는 것은 곧 생산성 저하와 직결됩니다.

    최근 서버리스 생태계에서 가장 주목받는 혁신은 바로 **SST(Serverless Stack)의 차세대 엔진 ‘Ion(v3)’**의 등장입니다. SST는 과감히 AWS CDK와 CloudFormation을 버리고, Pulumi 엔진을 내장하는 결단을 내렸습니다.

    20년 차 엔지니어의 관점에서 볼 때, 이는 단순한 도구의 변경이 아닌 **“서버리스 인프라 프로비저닝의 패러다임 시프트”**입니다. 본 글에서는 왜 우리가 SST Ion과 Pulumi에 주목해야 하는지 분석하고, 실제 프로덕션 수준의 Python Lambda 파이프라인을 구축하는 실전 가이드를 공유합니다.

    1. 왜 CloudFormation을 버려야 하는가? (SST Ion vs AWS CDK)#

    기존 AWS CDK 기반 아키텍처와 새로운 SST Ion(Pulumi 기반) 아키텍처의 핵심 차이는 **“인프라 상태를 누가, 어디서 결정하는가”**에 있습니다.

    [기존 CDK 방식]
TypeScript 코드 -> CDK Synthesis -> 대형 CloudFormation YAML 생성 -> AWS CloudFormation 엔진 전송 -> 순차적 리소스 프로비저닝 (매우 느림)

[SST Ion (Pulumi) 방식]
TypeScript 코드 -> SST Ion 엔진 (Pulumi Core) -> 종속성 그래프 분석 -> AWS API 직접 병렬 호출 (초고속)

    1) CloudFormation의 병목 요인#

    • 단일 트랜잭션 루프: CFN은 인프라의 일관성을 위해 상태 변경을 동기적으로 처리합니다. 리소스 하나가 생성될 때까지 다음 리소스는 대기 상태에 머물며, 롤백 발생 시 전체 스택이 잠기는 현상이 빈번합니다.
    • 무거운 엔진: AWS 내부에서 상태를 비교하고 유효성을 검증하는 과정 자체가 무겁게 설계되어 있습니다.

    2) SST Ion (Pulumi)의 혁신#

    • 병렬 API 프로비저닝: Pulumi 엔진은 로컬 혹은 빌드 머신에서 리소스 간의 종속성 그래프(DAG)를 직접 계산한 후, AWS SDK/API를 통해 여러 리소스를 동시에 병렬로 생성합니다.
    • 실시간 양방향 동기화: CloudFormation을 거치지 않기 때문에 ‘Live Lambda Dev’ 기능이 비약적으로 빨라집니다. 클라우드 리소스와 로컬 코드 간의 동기화가 거의 실시간(1초 미만)으로 이루어집니다.

    2. 실전 가이드: S3 이벤트 기반 이미지 메타데이터 추출 파이프라인 구축#

    이제 이론을 넘어 실무에 적용해 보겠습니다. 구축할 시나리오는 다음과 같습니다. 사용자가 S3 버킷에 이미지를 업로드하면, S3 이벤트가 AWS Lambda를 트리거합니다. Lambda는 해당 이미지의 메타데이터를 분석하여 가공한 뒤 로그를 남기는 구조입니다.

    SST Ion 환경에서는 인프라 정의는 TypeScript로 간결하게 작성하고, 실제 비즈니스 로직(Lambda)은 데이터 처리에 강점을 가진 Python으로 작성하여 결합도를 낮춥니다.

    1) SST Ion 인프라 정의 (sst.config.ts)#

    SST Ion을 사용하면 아래와 같이 직관적이고 압도적으로 짧은 코드로 S3, Lambda, 그리고 이벤트 연결을 선언할 수 있습니다.

    // sst.config.ts
export default $config({
  app(input) {
    return {
      name: "fast-image-processor",
      removal: input?.stage === "production" ? "retain" : "remove",
      home: "aws",
    };
  },
  async run() {
    // 1. 메타데이터를 저장할 S3 버킷 생성
    const bucket = new sst.aws.Bucket("ImageBucket");

    // 2. Python Lambda 함수 정의 및 S3 읽기 권한 부여
    const processor = new sst.aws.Function("MetadataExtractor", {
      handler: "src/handler.lambda_handler",
      runtime: "python3.11",
      copyFiles: [{ from: "src", to: "." }],
      link: [bucket], // SST의 강력한 'Link' 기능으로 환경 변수 및 권한 자동 주입
    });

    // 3. S3 업로드 이벤트와 Lambda 연결
    bucket.subscribe(processor, {
      events: ["s3:ObjectCreated:*"]
    });

    return {
      BucketName: bucket.name,
    };
  },
});

    2) 실전 구동 가능한 Python Lambda 코드 (src/handler.py)#

    다음은 S3 이벤트를 수신하여 업로드된 이미지의 메타데이터(크기, 콘텐츠 타입, 커스텀 태그 등)를 안전하게 추출하는 프로덕션 레벨의 파이프라인 소스 코드입니다. 이 코드는 별도의 무거운 이미지 라이브러리 없이 AWS SDK인 boto3만을 활용하여 즉시 구동 가능하도록 최적화되었습니다.

    import json
import logging
import urllib.parse
import boto3
from botocore.exceptions import ClientError

# 로깅 설정
logger = logging.getLogger()
logger.setLevel(logging.INFO)

s3_client = boto3.client('s3')

def lambda_handler(event, context):
    """
    AWS Lambda Handler: S3 ObjectCreated 이벤트를 수신하여 
    해당 오브젝트의 메타데이터 및 헤더 정보를 추출합니다.
    """
    logger.info("Received event: %s", json.dumps(event, indent=2))
    
    try:
        # S3 이벤트로부터 버킷 명과 객체 키 추출
        record = event['Records'][0]['s3']
        bucket_name = record['bucket']['name']
        # URL 인코딩된 파일명 대응 (한글, 공백 등)
        object_key = urllib.parse.unquote_plus(record['object']['key'], encoding='utf-8')
        
        logger.info(f"Processing object: {object_key} from bucket: {bucket_name}")
        
        # S3 HeadObject API 호출 (파일 전체를 다운로드하지 않고 메타데이터만 고속 조회)
        response = s3_client.head_object(Bucket=bucket_name, Key=object_key)
        
        # 유용한 메타데이터 정보 정제
        metadata_summary = {
            "Bucket": bucket_name,
            "Key": object_key,
            "ContentType": response.get('ContentType', 'unknown'),
            "ContentLengthBytes": response.get('ContentLength', 0),
            "LastModified": str(response.get('LastModified')),
            "ETag": response.get('ETag', '').replace('"', ''),
            "CustomMetadata": response.get('Metadata', {})
        }
        
        logger.info(f"Successfully extracted metadata: {json.dumps(metadata_summary)}")
        
        return {
            'statusCode': 200,
            'body': json.dumps({
                'message': 'Metadata processing completed successfully.',
                'target': object_key,
                'metadata': metadata_summary
            })
        }

    except ClientError as e:
        error_code = e.response['Error']['Code']
        error_message = e.response['Error']['Message']
        logger.error(f"S3 ClientError [{error_code}]: {error_message}")
        raise e
        
    except Exception as e:
        logger.error(f"Unexpected error occurred: {str(e)}")
        return {
            'statusCode': 500,
            'body': json.dumps({'error': str(e)})
        }

    3. 성능 비교 및 개발자 경험(DX)의 혁신#

    SST Ion을 도입했을 때 엔지니어가 체감하는 변화는 수치로 극명하게 나타납니다.

    평가 지표기존 AWS CDK / CFNSST Ion (Pulumi 엔진)개선 효과
    최초 인프라 배포 속도약 3분 ~ 5분약 15초 ~ 20초약 15배 속도 향상
    코드 변경 시 반영 속도약 1분 30초실시간 (Hot Reloading)대기 시간 제로(0)
    상태 관리 오버헤드CFN Stack Lock 발생 가능로컬/SST Console 실시간 추적디버깅 피로도 급감

    Live Lambda Dev의 마법#

    SST Ion은 로컬 컴퓨터와 실제 AWS 환경 간에 실시간 웹소켓 터널을 연결합니다. 과거에는 Lambda 코드를 한 줄 고치면 cdk deploy를 수행하고 1분을 기다려야 테스트가 가능했습니다. 반면 SST Ion 환경에서는 로컬에서 파일을 저장하는 순간, AWS로 들어오는 실제 이벤트가 로컬 서버의 Lambda 코드를 통과하여 실행됩니다. 클라우드의 리소스를 그대로 활용하면서 로컬에서 브레이크 포인트를 걸고 디버깅할 수 있게 된 것입니다.

    💡 시니어 엔지니어가 전하는 실무 적용 팁#

    1. 상태 파일(State File) 백업 경로 지정: SST Ion은 내부적으로 Pulumi의 상태 관리 메커니즘을 사용합니다. 프로덕션 환경을 운영할 때는 Pulumi Cloud SaaS 서비스를 연동하거나, 자체 S3 버킷을 State Backend로 지정하여 상태 잠금(State Lock) 및 이력 관리를 엄격히 통제해야 합니다.

    2. v2에서 v3(Ion) 전환 전략: 기존 SST v2는 AWS CDK 위에 구축되어 있어 완전히 다른 프레임워크 수준의 마이그레이션이 필요합니다. 한 번에 전체 서비스를 전환하려 하지 말고, 신규 마이크로서비스나 독립적인 이벤트 기반 파이프라인(예: 위 예시와 같은 이미지 배치 처리기)부터 단계적으로 도입하여 운영 노하우를 쌓는 것을 강력히 권장합니다.

    3. Python Lambda의 의존성 관리: Lambda에서 외부 라이브러리(예: Pillow, requests 등)가 필요할 경우, SST Ion의 python.installCommands 설정을 활용하여 requirements.txt 빌드 단계를 자동화할 수 있습니다. 이를 통해 빌드 아티팩트의 크기를 최소화하고 콜드 스타트를 방지하십시오.

    결론: 서버리스 개발의 새로운 표준#

    이제 “인프라 배포는 원래 느린 것"이라는 타협은 유효하지 않습니다. SST Ion과 Pulumi 조합은 단순한 속도 개선을 넘어, 개발자가 로컬과 클라우드의 경계를 느끼지 못하게 만드는 **압도적인 개발자 경험(DX)**을 선사합니다.

    느린 배포 속도로 인해 아키텍처 실험이 주저되었거나 개발 주기가 늘어지고 있었다면, 지금 즉시 CloudFormation의 껍질을 벗겨내고 SST Ion 도입을 검토해 보시기 바랍니다. 생산성 차이가 곧 경쟁력의 차이가 될 것입니다.
